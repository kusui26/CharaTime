# CharaTime 開発プラン v1.2（2026-09-10 初版、2026-09-11 改訂・再改訂）

`docs/260909_memo.md` の構想 —— au ガラケー時代の「ケータイパートナー（β版）」のように、iPhone の中でキャラクターが勝手に生きていて、アイテムで部屋を飾れるアプリ —— を、2026 年 9 月時点の iOS の制約と生成 AI の能力を実測・調査したうえで、個人開発の計画に落としたもの。

- 根拠となる調査報告（6 本、出典約 520 件）は `docs/research/` にある。本文では要点だけを引く（§13）。v1.1 で照合した別リサーチは `docs/260820_gpt.md`。
- 凡例: ✅ = 一次情報（Apple / OpenAI / Google / KDDI の公式文書、法令原文、App Store 実データ）で確認（2026-09-10）/ 🔶 = 二次情報 / 🔷 = 推測・設計判断
- 環境は本セッションで実測した（§1）。日付はすべて 2026 年。
- 本文中の `research/X` は `docs/research/X_*.md` を指す。

## 0. 結論（先に 10 行）

1. **メモの「iPhone のホーム画面でキャラを自由に動かす」は、文字通りには iOS で不可能**（アプリはホーム画面に描画できず、ウィジェットは 1 日 40〜70 回の静止画差し替え、アニメーションは非推奨ハックのみ ✅）。代わりに **5 つの「面」で分担**する: 核は**アプリ内の待受モード**（60fps で自由に歩く。ホーム画面のスクショの上も歩ける）、ホーム画面には**透過ウィジェット専用ページ**（本物の壁紙の上で 10 分ごとに姿と位置が変わる）、充電中は **StandBy**、外出時は **Dynamic Island の「いっしょモード」**（1・2・4 時間のセッション）、ロック解除のたびに違う場所にいる**壁紙セット**。PiP の小窓「おさんぽ」は実験枠。
2. **v1.1 の最大の変更は Phase 0 の「スパイク」**: キャラを作る前に、ウィジェットで「自分が何もしなくても動いて見える」（タイマー Text + マスクフォントの 1fps）が iOS 27 の実機で kill 後・ロック解除後も成立するかを確かめ、Go / Conditional Go / No-Go を決める（D-11）。公開 API 版の PoC にも「Xcode 26.1 以降の SDK でビルドすると iOS 26.1 以降で止まる」報告（GitHub Issue #3、作者未回答 ✅）があり、iOS 26.6 / 27 での動作は未確認なので、**Conditional Go（5 分ごとに様子が変わる窓）が有力**。どの結果でもプランは成立し、面 1 の約束（「まばたきしている」か「10 分ごとに変わる」か）だけが変わる。描画は `RenderCapability` の梯子で静止画まで自動フォールバックし、「キャラが消える」だけは起こさない。
3. **元ネタは一次資料で裏づけが取れたが、記憶とは 2 点ずれる**: ケータイパートナー（β版）は 2009-03〜2011-04 の無料 BREW 待受アプリで、アドレス帳・着信履歴・季節・センサーに反応して話しかける「対話型パートナー」（キャラは さくらこ・ソニック・はちゅねミク・Rody 等）✅。**サンリオキャラはおらず、アイテム購入・部屋の飾り付けもなかった** ✅。「壁紙の上を小さなキャラが歩き回る」体験の本流は docomo マチキャラ（2006〜、2026-11-30 終了予定）で、サンリオは後継の au one キャラタイム（2011〜、買い切り 315〜525 円）の HELLO KITTY（アート集）。CharaTime はこの 2 系統（歩き回る × 話しかける）を合成し、「アイテムで部屋を飾る」はメモの要望に応える新規要素として設計する。当時の不満（電池が一晩で空、時計が隠れる占拠感、消せない BGM）は反面教師にする。
4. **設計の中核は「日課エンジン」**: 日付と seed から 1 日の行動表を決定論的に生成し、任意の時刻の姿を O(1) で返す。ウィジェットが未来の姿を事前計算でき、アプリを閉じている間も「生きていた」場所にいて、全部の面が同じ一匹を見る。**行動は決定論、会話（吹き出しの文言）だけ将来オンデバイス AI に任せる**（D-12）。タップ反応はメモどおり後回し（割り込みとして後から足せる位置に置く）。
5. **キャラは 5 体のオリジナル**（画風「まるっとフラット」= 2 頭身・太い輪郭線・ベタ塗り・パステル。40pt で誰か分かることを採用条件にする。サンリオの識別要素は使わない）。1 体 11 枚（idle 2 / walk 4 / sit 1 / sleep 2 / happy 2）+ プロシージャル動作で足りる。**制作は ChatGPT Images 2.5（2026-09-08 公開、透明背景をネイティブ出力 ✅）を本命、Gemini Nano Banana 2 / Pro を第二、Claude を設計・QA・スクリプト担当**にし、キャラシート → 参照添付でポーズグリッド → Claude 採点 → 人間の手直し → 自動正規化の流れで **5 体 10〜15 時間・追加費用 0 円**。
6. **技術は Swift 6.3 / SwiftUI 単体描画 / WidgetKit / App Group / XcodeGen + 4 パッケージ**。SpriteKit は使わない（アプリとウィジェットで描画コードを共有するため。iOS 26.x の fps 退行 🔶 も回避）。歩数は Core Motion、天気は WeatherKit（将来）。TrainNow で確立した Claude Code の検証ループをそのまま移植する。
7. **13 週・7 フェーズ、各フェーズに Gate**: Phase 0（〜9/20）環境更新・スパイク・1 体目 → 1（〜10/4）待受モード → 2（〜10/18）5 体・部屋・アイテム（ミラーボール）→ 3（〜11/1）ホーム画面ウィジェット・透過・StandBy（Go なら疑似アニメ）→ 4（〜11/15）いっしょモード・壁紙・PiP 実験 → 5（〜11/29）自作キャラ取り込み → 6（〜12/13）公開判断。Phase 1 で止まっても「待受アプリ」として完成している順に積む。Phase 7 候補は AI 発言・タップ反応・バックアップ。
8. **ユーザーが今すぐやること**（2026-09-11 時点。骨組み 0-2・0-3 は完了）: (a) **9/14 までに iPhone の自動アップデートを切る**（設定 → 一般 → ソフトウェアアップデート → 自動アップデート を全部オフ。iOS 27 に上がると Xcode 26.6 から実機に入らなくなる）、(b) 最初の 1 体（推奨: ピヨ）を決める、(c) 10/19 までに Apple Developer Program（US$99/年）を判断（無料署名は 7 日で失効し常駐アプリと相性が最悪）。ディスク整理は完了済み（空き 185 GB）。macOS・Xcode・実機の iOS はすべて据え置き。
9. **費用はほぼ Developer Program のみ（年 1.5 万円程度）**。生成 AI は契約済みサブスク内。**公開は Gate 6（11/30）まで保留**。設計は公開にも耐える形にする（広告なし・買い切り中心、UGC は端末内完結から、外部 AI に送る前の同意）。アプリ名「キャラタイム」は旧登録（2009、ネオス）が 2019 年に満了と確認 ✅ で登録上の障害は見当たらないが、J-PlatPat で最終確認する。
10. **最大のリスク**は「本物のホーム画面を歩く」との期待差（R-1）、ウィジェット更新の粗さ（R-2）、疑似アニメが OS 更新で止まること（R-13）、生成 AI の一貫性（R-3）。いずれも設計で織り込み済みで、Phase 0 のスパイクと Phase 3 の実機 1 週間計測で確かめる。

| 「サンリオのようなキャラクター」 | **ケータイパートナーにサンリオキャラはいない** ✅。近いのは au one キャラタイムの HELLO KITTY（1974〜89 年のアート集で、動き回るキャラではない）、ぷち・ねこ、ソフトバンク版キャラタイムのハローキティ（2009-11）、ケータイパートナーの さくらこ／Rody／はちゅね。「サンリオ"のような"」は複数の記憶の混在と考えるのが自然 🔷 | `research/A` §5.1 |
| 「待受かホーム画面を自由に動いていた」 | **整合する**。ただし本流は docomo マチキャラ（壁紙の上を小キャラが歩く）。ケータイパートナーの さくらこ は顔が全画面で、ソニック・はちゅね・Rody は画面内を動き回る ✅ | 同上 |
| 「ミラーボールのようなアイテムを購入して配置」 | **ケータイパートナー／キャラタイムのどの一次資料にも記載がない** ✅。ケータイパートナーは終始無料で課金導線がなく、キャラタイムはタイトル買い切り。au で「アイテム課金」があったのは au one アバター（着せ替え）で、待受常駐キャラではない。史実で最も近いのは「集める」（トレカ、達成率、充電中にサムネが降る） | 同上 |
| 「ケータイパートナー（β版）が近い」 | 「ケータイに愛着を持つ」「人格を持ったかのような演出」という**狙いの面では正しい**。体験の形としては「壁紙の上を歩く小キャラ（マチキャラ）」と「話しかけてくるパートナー（ケータイパートナー）」の 2 系統の合成 | — |

**設計上の含意**: (1) サンリオ風の画風は「方向性」として採用してよいが、史実に縛られる必要はない。(2) 「アイテムを買って部屋を飾る」は**史実にない新規要素**なので、当時の仕様を探すのではなく、iOS の課金や部屋の表現に最も合う形（§5.6）で自由に設計する。(3) CharaTime は「歩き回る」×「話しかける」の合成を狙う。

### 2.4 「体験の核」（`research/A` §4 の P1〜P8）と CharaTime での扱い

| 優先 | 要素 | 当時の根拠 | CharaTime |
|---|---|---|---|
| P1 | **時間帯・季節・記念日で勝手に生活する** | ライフタイプ「24 時間 365 日生活」、ケータイ係長の生活アルゴリズム、キティの 11 記念日、ソニック「何でもないときにも走る・不機嫌になる」 | §5.4 の日課エンジン（核） |
| P2 | **端末イベントへの反応**（未読・不在着信・充電・開閉） | キャラタイムの 70 種の端末情報、マチキャラの本質 | iOS では通知内容は取れない。充電・時刻・（将来）天気・歩数・予定で代替 |
| P3 | **吹き出し・手紙・日記** | さくらこ「家族からメールが届いたよ〜」、ケータイ係長の秘密のメール、擬似メール | 時報・挨拶の吹き出し（Phase 1）。日記は将来候補 |
| P4 | 触る・振る・傾ける | はちゅね・ソニックのモーション反応 | メモの指示で後回し。割り込みとして後から足せる設計 |
| P5 | コレクション・達成率・ゆるい成長 | トレカ、充電中にサムネが降る、Rody のバリエーション増加 | 「育成」は入れないが、「見たシーン図鑑」は将来候補 |
| P6 | 季節・記念日限定の演出 | キティ記念日（当日は他画面に切替不可）、ケータイ係長 30 種 | 季節アイテム（Phase 2 以降） |
| P7 | 複数キャラ・着せ替え・**部屋とアイテム** | 複数コンテンツ切替、ぷち・ねこ「部屋に紛れ込む」、アバターのアイテム課金 | **史実にない新規要素だが、メモの要望なので中核に置く**（§5.6） |
| P8 | 嗜好学習・レコメンド | KDDI の中核コンセプト | やらない（当時「コンテンツの入り口」と不評） |

### 2.5 反面教師（2009 年のユーザー評から）

当時のブログは、表情変化・通知・日記・質問を「どこでもいっしょ的」と好意的に受け止めつつ、結論を「無料だけど使いたくない」としている ✅。理由と CharaTime の対策:

| 当時の不満 | 対策 |
|---|---|
| **電池が一晩で空**（満充電でも朝のアラームが最後） | 待受モードは充電スタンド前提、夜モード、静止中 30fps、非表示で停止（§7.5）。ウィジェットは OS の予算内 |
| 時計・電波・電池すら見えない**占拠感** | 待受モードは時計・電池を常に表示（ガラケー待受の再現）。ウィジェットは小さく、「でしゃばらない」 |
| 通知から本来の操作へ進めない | 通知はそもそも扱わない |
| 消せない BGM・止まらない演出 | 音はデフォルト OFF、演出は数秒で終わる |
| 私的空間（待受）への公的情報の押し込み | ニュース・レコメンドを出さない |

設計原則は当時のユーザーの言葉を借りて **「でしゃばらない程度にケータイを彩る」**。

## 3. プロダクト定義

### 3.1 一言で

**「iPhone の中に住んでいて、見ていないあいだも勝手に生きているキャラクター」。** ガラケーの待受にいたあの子を、2026 年の iPhone で許される手段をすべて使って再現する。タグライン候補: 「iPhone の中に、ひとり住んでいる。」（`260820_gpt.md` §2）。

ケータイパートナー／キャラタイム／マチキャラの体験を分解すると、価値の中心は「アニメーションの滑らかさ」ではなく次の 3 点だった（`research/A` §4 の P1〜P3・P7 を圧縮。§2.4）。

1. **常にそこにいる**（待受 = 端末を開くたびに目に入る）
2. **勝手に生きている**（時刻で行動が変わる、放っておいても何かしている、たまに話しかけてくる）
3. **自分の部屋にできる**（アイテムを買って置く、キャラを選ぶ）

iOS では 1 が最も難しい。だから本プランは「1 を複数の面（§4）で分担し、2 と 3 をアプリ内で最大化する」構成を取る。設計原則は当時のユーザー評から借りて「でしゃばらない程度にケータイを彩る」（§2.5）。

### 3.2 ターゲットと利用シーン

| 優先 | 誰 | シーン |
|---|---|---|
| 1 | **開発者自身**（自分用アプリとしてまず完成させる） | 机の上のスタンドに置いた iPhone（充電中）で待受モード / ホーム画面の 1 ページを「キャラの部屋」にする / ロック解除のたびに位置が変わる壁紙 |
| 2 | ケータイパートナー・マチキャラ世代（30〜40 代） | 「懐かしい」で入って「今も動いている」で残る |
| 3 | ホーム画面カスタマイズ層（透過ウィジェット・アイコン着せ替えのユーザー、`research/D` §1） | 透過ウィジェットの延長として「動く住人」を置く |
| 4 | 自分のキャラを動かしたい層（生成 AI 利用者） | 「キャラ工房」で自作キャラを取り込む（Phase 5） |

公開の意思決定は Gate 6 まで保留する（§12 未決 Q-1）。それまでは**自分の iPhone 17 Pro で 3 ヶ月使い続けられるか**を唯一の評価軸にする。

### 3.3 スコープ

| 段階 | 入れるもの | 入れないもの |
|---|---|---|
| **MVP**（Phase 0〜2） | 待受モード（アプリ内フルスクリーン）、キャラ 5 体と選択、日課エンジンによる自律行動、時計・時報、部屋 3 系統（同梱イラスト / 写真 / ホーム画面スクショ）、アイテム 5 種（ミラーボール含む）と配置 | タップ反応（メモの指示で後回し）、音、課金、ネットワーク |
| **v1**（Phase 3〜4） | ホーム画面ウィジェット（透過方式含む）、StandBy、Live Activity（Dynamic Island・ロック画面）、壁紙セット書き出し、Tier 2 ポーズ、ウィジェットの 1〜8fps 疑似アニメ（実験枠）、PiP「おさんぽ」（実験枠） | — |
| **v2**（Phase 5〜） | キャラ工房（自作画像の取り込み → 端末内切り抜き → 登録）、将来はアプリ内生成（API） | — |
| **見送り** | — | Android 版、Apple Watch 文字盤、複数キャラ同時表示、キャラ同士の交流、育成（レベル・寿命）、PiP 常駐（§4.5） |

「育成」を入れないのは意図的である。ケータイパートナー系の魅力は「世話をしないと死ぬ」プレッシャーではなく「勝手に生きている」安心感にあり、育成要素は放置罪悪感を生んで離脱を早める（デスクトップマスコット系の知見、`research/D` §4）。

### 3.4 成功の定義

| 指標 | 目標 | 測り方 |
|---|---|---|
| 自分のホーム画面に残っているか | Gate 3 から **90 日後も外していない** | 事実 |
| 待受モードの利用 | 週 3 日以上、机の上で点けている | アプリ内の簡易ログ（端末内のみ） |
| 「生きている」感 | 1 日の日課を見て「今日は何してた？」と思える。行動のパターンが 1 週間でバレない | 自己評価 + 日課の多様性をテストで数値化（Segment の種類数・遷移のエントロピー） |
| キャラの品質 | 5 体すべてが 60pt でも識別できる。ポーズ間で別人にならない | コンタクトシート目視 + Claude の画像判定 |

### 3.5 先行アプリとの差別化（`research/D` §1・§8）

市場の上位は Widgetable（US 38 万件 ★4.92、Google Play 5,000 万 DL）、Pixel Pals（US 3.7 万件 ★4.58、個人開発の最大成功例。2023 年に約 5 万サブスク・四半期約 62.5 万ドルの推計 🔶）、iScreen（US 15 万件）。共通する不満は **「広告地獄」「有料だらけ」「観るだけ」「アプリの外では動かない」「データ消失」** ✅。「Shimeji を iPhone で」という需要は明確で、偽アプリ（静止画を壁紙にするだけ）が ★1.8 でも 225 件の評価を集め、Mooshi（1.6 万件）には「ホーム画面を歩くと思った」という失望が並ぶ ✅。日本では個人開発の PixelPot（歩数で育つ植物ウィジェット × AI 生成イラスト、★4.78・9,812 件）が「個人 × ウィジェット × AI 生成」が審査を通り評価されることを示している ✅。「写真から自分のペットをキャラ化」する直接競合 **SpritePals: Pixel Pet Widget**（個人開発、2026-01 公開、iOS 17+、US ★3.9・8 件、無料 + 生成トークン $0.99〜 + Pro 買い切り $5.99、年齢 4+）は、写真を Cloudflare Worker 経由で OpenAI に送って生成し ✅、不満は「カスタム生成が毎回有料」「Dynamic Island の表示が消える」「表情が単調」（`research/F` §1）。

CharaTime の差は次の 5 つに置く。

1. **1 匹が複数の面で一貫して生きている**（待受・ウィジェット・StandBy・ロック画面・壁紙が同じ日課を見ている）。先行アプリは DI かウィジェット 1 枚に閉じている
2. **部屋とアイテム**（ミラーボールで踊る等、アイテムが行動の語彙を増やす）。「部屋」を持つ先行アプリはごく少数
3. **ホーム画面スクショの上を歩く待受モード**と**透過ウィジェット**（ガラケーの「アプリが並んだ画面を歩く」に最も近い 2 つの見せ方）
4. **義務のない設計**（餌・成長・連続ログインなし。「観るだけ」を欠点でなく本質にする。Pixel Pals の「常にそこにいる」が価値だったという学び）
5. **自作キャラを動かせる**（Phase 5）。SpritePals と違い、段階 1 は端末内完結・無料・写真をサーバーに送らない。公開するなら広告なし・買い切り中心（この層の最大の不満を最初から排除）

### 3.6 設計原則（6 つ）

`260820_gpt.md` §4 の 5 原則に、当時のユーザー評（§2.5）から得た 1 つを加える。迷ったらここに戻る。

| 原則 | 意味 | 本プランでの具体化 |
|---|---|---|
| **Ambient First** | アプリを開いていなくても「存在している」と感じられる。ゲーム画面を開かないと成立しない体験にしない | 面 1〜4（§4）。日課エンジンが閉じている間も「生きていた」場所を返す（§5.4） |
| **Glanceable** | 1〜2 秒ホーム画面を見るだけで「今何をしているか」が分かる | シルエットで判別できるキャラ（§5.1）、行動ごとに姿勢が明確に違うポーズ（§5.3） |
| **No Punishment** | 放置しても死なない・病気にならない・通知で世話を要求しない。久しぶりに見たら嬉しそうにする程度 | 育成・空腹・寿命なし（D-09）。割り込みは「ご褒美」だけ（§5.4） |
| **Local First** | 状態・記憶・処理を端末内で完結。アカウント・バックエンド・広告・トラッキングなし | App Group の JSON、UGC は端末内切り抜き（§6.7 段階 1）、将来の発言生成もオンデバイス優先（D-12）。権限は機能を ON にした時だけ求める（Just-in-Time） |
| **Graceful Degradation** | 特殊なアニメ実装が OS 更新で止まっても、キャラそのものは消えない | RenderCapability の梯子（§7.5）: 疑似アニメ → 2 秒トランジション → 静止画 |
| **でしゃばらない** | 私的空間である待受を占拠しない。電池を食わない、時計を隠さない、音を鳴らさない | §2.5 の反面教師。夜モード・30fps・音は既定 OFF・ニュースやレコメンドを出さない |

## 4. iOS で「ホーム画面にキャラ」をどこまで実現できるか（最重要判断）

詳細は `research/B_ios_surface_feasibility.md`（Apple 公式文書を中心に出典 93 件）。ここでは事実 → 比較 → 採用構成 → 各面の設計の順に書く。

### 4.1 動かせない事実（2026-09-10 時点、iOS 26 / iOS 27 RC）

| 事実 | 根拠 |
|---|---|
| **アプリがホーム画面上に自由描画する手段は存在しない**。Android の overlay 権限に相当する API がなく、脱獄ツール（Shijima, 2024）でしか実現されていない | ✅ WidgetKit 文書「ウィジェット拡張は別プロセスで描画され、表示中でも継続的にアクティブではない」／`research/D` §3 |
| ホーム画面で「動く」のはウィジェットと Live Activity だけで、どちらも **OS が静的スナップショットを差し替えるモデル** | ✅ Apple「Keeping a widget up to date」 |
| ウィジェットの更新予算は **1 日 40〜70 回（15〜60 分に 1 回相当）**。エントリは約 5 分以上離す。アニメーションはエントリ切替時の最大 2 秒のトランジションのみ。常時表示（減光時）はアニメーションなし | ✅ 同上／「Animating data updates」 |
| 秒刻みの疑似アニメ（`Text(timerInterval:)` + コマ絵フォント）は可能だが、**Apple DTS が「サポート外・バッテリー消費・推奨しない」と明言**。ただし Pixel Pals（2022〜）が同系の手法で App Store に現存し、却下事例は見つからない | ✅ Apple Developer Forums の DTS 回答／🔶 |
| Live Activity は **最長 8 時間で自動終了**（ロック画面に最大 +4 時間）。ペイロード 4 KB。push 更新は有料アカウント必須 | ✅ ActivityKit 文書・DTS 回答 |
| ウィジェット拡張のメモリ上限は **30 MB** | ✅ Apple エンジニアのフォーラム回答 |
| iOS 18/26 の「着色」「クリア」外観では **システムがウィジェット背景を強制的に除去して Liquid Glass に置き換える** → 透過ウィジェット手法はライト/ダーク外観でしか成立しない | ✅ Apple「Optimizing your widget for accented rendering mode」 |
| 壁紙をアプリから設定する API はない。写真シャッフル（タップ時 / ロック時 / 1 時間ごと / 1 日ごと、アルバム指定可）とショートカットの「壁紙を設定」（時刻オートメーションは毎日 / 毎週 / 毎月のみ、確認なし実行可）だけ | ✅ Apple サポート |
| **PiP（`AVSampleBufferDisplayLayer` + `AVPictureInPictureController`）だけが、ホーム画面や他アプリの上で 10〜30fps の自由な動きを出せる公開 API**。窓は不透明・角丸、位置はユーザー任せ、動画再生と排他。非動画 PiP アプリ（メモ・時計）は 2021 年から審査を通り 2026 年も更新中 | ✅ Apple AVKit 文書／App Store 実例 |
| iOS 27（2026-09-14 公開予定）にウィジェット / Live Activity のアニメーション新 API はない。新要素は `systemExtraLargePortrait`、Dynamic Island の横向き表示、StandBy の `activityBackgroundTint`、`LiveActivityIntent`。**Xcode 27 は macOS 26.6 以上が必須**（ローカルは 26.5.2） | ✅ WWDC26 セッション 277・223、Xcode 27 リリースノート |
| 無料の Personal Team でも App Groups・Widget Extension・ローカル Live Activity は使える。Push・TestFlight・7 日超の実機インストールは Developer Program（US$99/年） | ✅ Apple「Supported capabilities (iOS)」 |

結論: **メモの「ホーム画面でキャラを自由に動かす」は、文字通りには iOS では不可能**。できるのは (a) アプリ内で本物そっくりの待受を作る、(b) ホーム画面に「10 分ごとに様子が変わる透明な窓」を置く、(c) 充電中の StandBy と Dynamic Island に住まわせる、(d) 壁紙そのものを時間帯で差し替える、(e) PiP の小窓で連れ歩く、の 5 つで、それぞれ「動きの質」と「常駐性」がトレードオフになる。

### 4.2 面ごとの比較

| 面 | 動きの質 | 常駐性 | 審査リスク | 工数 | 電池 | 主な制約 |
|---|---|---|---|---|---|---|
| **面 0: 待受モード（アプリ内）** | ◎ 60〜120fps、自由に歩き回る | △ アプリを開いている間だけ（消灯抑止・充電スタンド前提） | 低 | 小 | 中〜大 | ホーム画面ではない |
| **面 1: ホーム画面ウィジェット** | △ 5〜10 分ごとの静止画 + 2 秒トランジション（+ 実験枠の 1〜8fps 疑似アニメ） | ◎ 置きっぱなし | 低〜中 | 中 | 小 | 30 MB、透過はライト/ダーク限定、予算 40〜70 回/日 |
| **面 2: StandBy** | △ ウィジェットと同じ（Live Activity なら全画面 2 倍） | ○ 充電・横置き・ロック時 | 低 | 小（面 1 の派生） | 小 | 背景は必ず除去、夜は赤ティント |
| **面 3: Live Activity / Dynamic Island** | △ 2 秒トランジション + 疑似アニメ。位置は固定領域 | ○ 8 時間（ロック画面 +4h）。Mac・Watch・CarPlay に波及 | 低〜中（Pixel Pals 前例、HIG の建前とはずれる） | 中 | 小〜中 | 4 KB、8 時間、更新はアプリ前面時のみ（push は有料） |
| **面 4: 壁紙** | × 静止画。1 時間〜数時間粒度で位置が変わる | ◎ 常に壁紙 | なし | 小〜中 | ほぼ 0 | 順序制御不可（シャッフル）/ 手動セットアップ（ショートカット） |
| **面 5: PiP「おさんぽ」** | ○ 10〜30fps、窓内で自由 | ○ 閉じるまで。他アプリの上でも | 中（実例多数だがペット用途の前例なし） | 中〜大 | 中〜大 | 不透明な角丸窓、透明不可、動画と排他、実機のみ |
| ロック画面ウィジェット / 常時表示 | × 分単位の静止画、モノクロ | ◎ | 低 | 小 | 小 | 小さい、vibrant |

### 4.3 採用する構成（決定 D-02）

「自律的に動き回る」要件を満たすのは面 0 と面 5 だけで、面 1〜4 は「様子が変わる」演出である。したがって:

1. **面 0 を核にする**（Phase 1〜2）。ここに「勝手に生きている」体験をすべて作り込む。
2. **面 1 で「ホーム画面にいる」を実現する**（Phase 3）。ウィジェット専用ページ + 透過ウィジェットで「本物の壁紙の上を 10 分ごとに動く」。これがメモの要望に最も近い形。
3. **面 2 は面 1 の派生としてほぼ無料で得る**（Phase 3）。充電スタンドに置いたときの「待受」。
4. **面 3・面 4 は「連れ歩く」「起こすたびに違う」の演出として追加する**（Phase 4）。
5. **面 5（PiP）は Phase 4 の実験枠**。自分用なら審査は関係なく、「他のアプリを使っている間も画面の隅で歩いている」体験を試す価値はある。公開時に採否を決める（Q-9）。
6. 無料アカウントの期間は push に依存しない設計にする（面 1・3 ともローカル更新で完結）。
7. **面 1 が「動く窓」になるか「様子が変わる窓」に留まるかは、Phase 0 のスパイク（§9 Phase 0、D-11）で実機確認してから決める。** どちらでもプランは成立する（後者は Conditional Go）。スパイクの結果でキャラのポーズ設計（低 fps でも自然に見える単純な動き）と面 1 の約束事（「10 分ごと」か「まばたきしている」か）を確定する。

すべての面が §5.4 の同じ日課エンジンを見るので、「ウィジェットで見た姿」「アプリを開いた姿」「ロック画面の姿」が矛盾しない。これが「一匹が住んでいる」感の土台になる。

### 4.4 各面の設計

#### 面 0: 待受モード（アプリ内）

- フルスクリーン。背景は (a) 同梱の部屋、(b) 写真、(c) **ユーザーのホーム画面のスクリーンショット**（アイコンが並んだ画面の上をキャラが歩く。メモの「アプリが並んでいる画面」の最も直接的な再現）。(c) では床の範囲（キャラが歩ける帯）をユーザーがドラッグで指定する。
- ガラケー風の時計・日付・電池表示（ON/OFF 可）。毎正時の時報。
- `isIdleTimerDisabled` は待受モード表示中のみ true（Apple の指針どおり、不要になったら戻す ✅）。長時間の据え置きは iOS の「アクセスガイド」も案内する。
- 夜モード（22 時以降は自動で暗く）、静止中は 30fps、非表示で停止（§7.5）。
- 想定シーン: 机の充電スタンド、就寝前のナイトテーブル。

#### 面 1: ホーム画面ウィジェット（透過ウィジェットで「壁紙の上を歩く」）

- **ウィジェット専用ページ**: アプリアイコンを App ライブラリに退避してページからすべて外し、**Large（4×4）+ Medium（4×2）で 1 ページ（4 列 × 6 行）を埋める** ✅/🔶。Large = 部屋の全景、Medium = 時計 + キャラの近影、または部屋の続き。
- **透過ウィジェット**: 壁紙のスクリーンショット（ホーム画面編集モードで空ページを表示して撮る）をアプリに取り込み、機種 × ウィジェット位置ごとの矩形で切り抜いて `containerBackground` に敷く。iPhone 17 Pro は iPhone 16 Pro と同じ 2622×1206px ✅ なので、Widget-Blur の公開座標表（2622px、iOS 18 で確認: small 486 / medium 1032 / large 1098 px、left 87 / right 633、top 261 / middle 872 / bottom 1485 🔶）を初期値にできる。**iOS 26（Liquid Glass）での計測は未確認**なので、アプリ内に「スクショの上でガイド線をドラッグして合わせる」キャリブレーション画面を持つ。
- **成立条件**: ホーム画面の外観がライト / ダークのとき（着色 / クリアではシステムが背景を除去して着色するため疑似透過は崩れる ✅）。壁紙を変えたら再取得。写真シャッフル壁紙とは両立しない。アプリ内でこの条件を明示する。
- **タイムライン**: 5 分刻み × 4〜6 時間（48〜72 エントリ）+ 毎正時、`.atEnd` で再読込。設定変更時のみ `reloadAllTimelines()`。これで「10 分ごとに位置と姿が変わる」を約束できる。
- **描画モード**: フルカラー時は `.widgetAccentedRenderingMode(.fullColor)`、着色 / クリア時はシルエットで成立するデザインに切り替える（`research/E` §2.1）。
- **疑似アニメ（Phase 0 スパイクで判定）**: `Text(timerInterval:)` + マスク用カスタムフォントで、まず 1fps の「まばたき・呼吸」、次に 2〜4fps の歩行を試す。DTS 非推奨のため `RenderCapability`（§7.5）の最上段に置き、失敗したら自動で「5 分ごとの静止画 + 2 秒トランジション」に落ちる。設定で OFF にできるようにする。30fps は追わない（2 頭身キャラは低 fps の方が「らしい」）。**注意**: 公開 API 版 PoC（Bryce Bostwick）には「iOS 26.2 で動かない」Issue（2025-12-30、作者未回答）があり、報告者は「Xcode 26.1.1 でビルドすると壊れ、26.0.1 なら動く」としている ✅。私用 API 版（`_clockHandRotationEffect`）でも「iOS 26.1 以降の SDK でリンクすると止まる」報告が複数ある 🔶。iOS 26.6 / 27 での動作は未確認（`research/F` §2）。したがってスパイクは **Xcode 27 でビルドして**判定し、その前に既存アプリ（Pixel Pals、秒時計 for Widget）を実機に入れてウィジェットが秒単位で動くかを 5 分で確かめる。
- **タップ反応（後回し）**: iOS 17+ のウィジェットは `Button`（AppIntent）を置けて、その再読込は予算に数えられない ✅。「なでる」「呼ぶ」ボタンを足すのは Phase 4 以降の候補（メモの指示でまず自律行動に集中、D-09）。
- 小ウィジェット（2×2）は「顔 + 一言」の近影用。ロック画面ウィジェット（circular / rectangular）は顔のシルエット。

#### 面 2: StandBy（充電スタンドの待受）

- 充電中・横向き・ロック中に、小ウィジェット 2 つが背景除去で拡大表示される ✅。左に「部屋の一部 + キャラ」、右に「時計」の組み合わせを StandBy 用に最適化する（`disfavoredLocations` で不向きなウィジェットを除外）。
- StandBy 中の更新は「システム定義のレートで、予算にカウントされない」✅ ので、面 1 より頻繁に様子が変わる可能性がある（実機で計測、Phase 3）。
- 夜間は赤ティントの vibrant 表示 → シルエットで成立するデザインが必要。iPhone 17 Pro は常時表示対応 ✅。
- Live Activity を開始していれば、タップで全画面（200%）の「1 枚絵の待受」になる（面 3）。

#### 面 3: Live Activity / Dynamic Island「いっしょモード」（時間を区切ったセッション）

- **「24 時間常駐するペット」としては使わない**。HIG は Live Activity を「開始と終了が明確な、8 時間を超えない活動」向けと定めており ✅、8 時間で自動終了する。代わりに **「いっしょに過ごす: 1 時間 / 2 時間 / 4 時間」** をユーザーが選んで開始し、終わりに「またあとでね」と挨拶して終了するセッションにする（`260820_gpt.md` §35）。審査でも「Companion Session」として説明でき、体験としても「一緒にいた時間」が区切られて残る。
- iOS 26 の「スケジュール開始」API で起床時刻に自動開始できるが通知を伴う ✅ ので、既定は手動開始。
- コンパクト表示: 左にキャラの顔、右に状態アイコン（歩き / 昼寝 / 踊り）。拡張表示: 部屋の横長ストリップ。ロック画面: 横長の部屋。StandBy: 全画面。macOS 26 なら Mac のメニューバーにも自動表示 ✅。
- **更新はアプリを開いたときだけ**（無料アカウントでは push が使えず、バックグラウンド実行は「ほぼ制御できない」✅）。それでも日課エンジンは時刻から状態を出せるので、アプリを開くたびに「その時刻の正しい姿」に更新される。動きは疑似アニメ（`RenderCapability`、スパイクの結果に準じる）に頼る。期待値を「顔が Dynamic Island にいる」に置き、セッションの残り時間（`Text(timerInterval:)` で自動更新 ✅）を表示して、終わりが来ることを正直に見せる。
- 4 KB のペイロード制約 → `ContentState` は行動・位置・向き・フレーム番号だけ。

#### 面 4: 壁紙「起こすたびに違う場所にいる」

- **方式 A（写真シャッフル）**: アプリが「壁紙 + キャラ（位置・ポーズ違い）」を 12〜24 枚、写真アプリの専用アルバムに書き出す → ユーザーがロック画面の写真シャッフルで「ロック時」または「1 時間ごと」+ アルバム指定。順序はランダムなので時間帯とポーズは一致しないが、設定は 1 分で済む。枚数上限（16 枚で頭打ちという報告 🔶）に注意。
- **方式 B（ショートカット）**: アプリが App Intent「今の時刻の壁紙を返す」を提供し、ユーザーが「時刻オートメーション（朝 / 昼 / 夕 / 夜の 4 本）→ 壁紙を設定」を登録。決定論的で、確認なしに実行できる ✅。1 時間ごとの繰り返しトリガーはない ✅ ので粒度は数時間。
- 壁紙の元画像はユーザーの写真か同梱の部屋。ホーム画面側は同じ画像またはぼかし。面 1 の透過ウィジェットとは両立しない（壁紙が変わると切り抜きがずれる）ので、ユーザーにどちらかを選ばせる。

#### 面 5: PiP「おさんぽモード」（実験枠）

- `AVPictureInPictureController.ContentSource` + `AVSampleBufferDisplayLayer` に、CTRender の描画を `ImageRenderer` でラスタライズして 10〜15fps で流す（Mirrativ の「静的レイヤーを事前ラスタライズし、動く層だけ毎フレーム」が参考 ✅）。
- 窓は不透明・角丸で、位置は画面の四隅にスナップする。**四隅ごとに壁紙の該当部分を背景に敷けば疑似透過になる**（面 1 と同じスクショを流用）。
- 動画再生・通話と排他。バッテリーは面 0 と同程度。ホーム画面編集中は隠れる。
- 公開する場合の審査: PiP 固有の条文はなく 2.5.4（バックグラウンドは本来目的のみ）・2.4.2 が関係。「ユーザーが自分で開始・停止する観賞用表示」として説明し、無音オーディオ等の常駐ハックは使わない。ペット用途の前例がないため中リスク。

### 4.5 やらないこと

- 真のオーバーレイ（不可能）、脱獄前提の機能。
- バックグラウンドで無音オーディオや位置情報を流して常駐する手法（2.5.4 違反、電池）。
- `BGTaskScheduler` に依存した「裏で生き続ける」設計（実行タイミングは「ほぼ制御できない」✅）。決定論の日課エンジンなら不要。
- 無料アカウントの間の push 更新（Live Activity / WidgetKit push）。
- iOS 27 の新 API 待ち。ウィジェットのアニメーション制約は変わらない。

## 5. キャラクターと自律行動の設計

### 5.1 世界観と画風ガイド（オリジナル IP として作る）

メモの「サンリオのようなキャラクター」は**画風の方向性**として採用し、既存 IP の要素（特定キャラのリボン・耳の形・ひげ・口なし等）は使わない（§11 の法務リスク、`research/D` §7）。生成 AI に渡す「スタイル定義」を最初に文章で固定し、全キャラ・全ポーズで同じ文言を使う。これが一貫性の土台になる。

| 項目 | 方針 | 理由 |
|---|---|---|
| 頭身 | **2〜2.5 頭身**。頭がほぼ円、胴は頭の 0.6〜0.8 倍 | ガラケー待受（縦 240〜480px 時代）で成立していた比率。小さく描いても判別できる |
| シルエット | 丸を基本にし、**キャラごとに 1 つだけ特徴的な突起**（耳・とさか・アンテナ・しっぽ） | 60pt 程度のウィジェット表示でも見分けがつく |
| 線 | **一定太さの濃色の輪郭線**（黒 or 各キャラの最暗色）。線の内側で形が完結する | 背景除去が安定する。ガラケー時代の「はっきりした線」の再現 |
| 塗り | ベタ塗り + **1 段の影**（グラデ・テクスチャなし） | 生成のたびに変わる要素を減らし、ポーズ間の差を抑える |
| 色 | 1 キャラ **3〜4 色**、パステル基調。キャラ間で主色を重ねない（白・黄・茶・薄紫・ミント…） | 一目で誰か分かる。色数固定は一貫性の指示にも使う |
| 顔 | 点目 + 小さな口。表情差分は目と口だけで作る | 表情フレームの生成が安定する |
| 装飾 | 最小限（1 点まで） | ポーズ間で装飾が消える・変わる事故を防ぐ |
| 向き | 正面・左向き（右向きは反転）・後ろ向きの 3 種で全ポーズを設計 | 反転で枚数を半減。左右非対称な装飾は避ける |
| 影 | **画像には描かない**（アプリ側で足元に楕円影を別描画） | 床の色が背景ごとに変わっても自然。位置合わせもしやすい |
| 小サイズ可読性 | **24pt（Dynamic Island のコンパクト表示）と 40pt（小ウィジェット）で「誰か」「何をしているか」が読める**ことを採用条件にする。生成した全ポーズを 40pt に縮小したコンタクトシートで確認 | ホーム画面では小さく表示される時間が最も長い（`260820_gpt.md` §16 の要件を採用） |
| 画風の名前 | 社内用語として「**まるっとフラット**」と呼ぶ。プロンプトでは英語のスタイル定義文を固定（§6.3） | 呼び名があるとレビュー・修正指示が速い |

「ドット絵（ピクセルアート）」は採用しない（🔷）。理由: (1) ユーザーの記憶（サンリオ風）はベタ塗りイラスト寄りで、史実のケータイパートナー／キャラタイムも Flash のイラスト（§2.2）、(2) 生成 AI のドット絵はグリッドが揃わず後処理が重い、(3) iPhone の高解像度ではベタ塗りの方が映える。`260820_gpt.md` §20 はドット絵を推す（小さくても識別しやすい、低 fps でも違和感が少ない、フレーム数を抑えられる）が、これらの利点は「単純なシルエット・少ない色数・2 頭身」で満たせる。「レトロ・ドット絵パック」は将来の追加スタイル候補として残す（PixelLab 等の専門ツールがある。`research/C` §1.4）。

### 5.2 初期ロスター（案・5 体）

メモの「まず何種類か作って選べるように」に対し、**シルエット・主色・性格（行動の偏り）がすべて異なる 5 体**を提案する。名前は仮。世界観は「iPhone の中の小さな部屋に住んでいる住人たち」。

| # | 仮名 | モチーフ | 主色 | 特徴的な突起 | 性格パラメータ（§5.4） | 好きなアイテム |
|---|---|---|---|---|---|---|
| 1 | モチ | 白いまるい猫っぽい何か | 白 + 桃 | 小さな三角耳 | 活動 0.3 / 夜型 0.4 / 昼寝多め | クッション |
| 2 | ピヨ | ひよこ | 黄 + 橙 | とさか 1 本 | 活動 0.9 / 朝型 0.9 / よく歩く | ボール |
| 3 | クマオ | くま | 茶 + クリーム | 丸耳 | 活動 0.4 / 中間 / 座るのが好き・食いしん坊 | ソファ・おやつ |
| 4 | フワ | おばけ | 薄紫 + 白 | 頭のとんがり | 活動 0.6 / 夜型 0.9 / ミラーボールで踊る | ミラーボール |
| 5 | チップ | 小型ロボ | ミント + 灰 | アンテナ | 活動 0.5 / 規則正しい / 時報が好き・充電に反応 | 時計・充電器 |

最初に作るのは **1 体（ピヨかモチ）** で、パイプラインが安定してから残り 4 体を量産する（Phase 0 → Phase 2）。5 体で「選べる」感は十分に出る。以降は季節キャラ・コラボ枠として増やす。

### 5.3 アセット仕様（1 キャラあたり）

**Tier 1（MVP 必須、11 枚）** — これだけで §5.4 の全行動が成立する。

| ポーズ | 枚数 | 向き | 用途 |
|---|---|---|---|
| idle | 2（目開き / まばたき） | 正面 | 立ち止まり・時報 |
| walk | 4 | 左向き（右は反転） | 移動。4 枚を 8〜12fps で回す歩行ループ（実機で調整） |
| sit | 1 | 正面 | 座る（クッション・ソファ・床） |
| sleep | 2（呼吸の 2 段階） | 正面 or 横 | 睡眠・昼寝 |
| happy | 2 | 正面 | 喜ぶ・踊る（ミラーボール）・起床の伸び |

**Tier 2（Phase 4 以降、+7 枚）**: walk_back 2（奥へ歩く）、surprised 1、eat 2、stretch 1、look_up 1。

**Tier 0（UGC の最小、1 枚）**: 正面 idle 1 枚だけでも、§5.5 のプロシージャル動作（はねる・傾く・反転）で動かせる設計にする。ユーザー生成キャラの導入障壁を最小にするため。

**画像規格**

| 項目 | 値 | 理由 |
|---|---|---|
| 生成解像度 | 1024×1024 以上（キャラシートは 2K〜4K） | 後処理で縮小する前提。詳細は `research/C` |
| 正規化後（アプリ用 `hero`） | 512×512 PNG、透過、**足元の接地線を高さの 88% に固定**、キャラの身長を 400px に統一（キャラごとの体格差は manifest の `scale` で表現） | 全キャラ・全ポーズで「同じ位置に立つ」。位置合わせをコードに持ち込まない |
| ウィジェット用 `mini` | 256×256 PNG | ウィジェットのメモリ上限対策（`research/B` §2）。読み込むのは表示する 1 枚だけ |
| 命名 | `<charaId>_<pose>_<frame>.png`（例 `piyo_walk_02.png`） | スクリプトとマニフェストで機械的に扱う |
| マニフェスト | `characters.json`（id, 表示名, scale, palette, personality, poses: {pose: [frames]}, anchor） | アプリ・ウィジェット・パイプラインの単一の真実 |

### 5.4 自律行動の設計 — 「日課エンジン」（決定論・時刻駆動）

メモの「まずは自律的に動く（タップ反応は後回し）」を、**時刻を入力にした決定論的シミュレーション**として設計する。これは見た目の都合ではなく、iOS の制約（§4）から必然的に導かれる設計判断である。

**なぜ決定論か**

1. ウィジェットはアプリと別プロセスで、しかも「未来の時刻の見た目」を前もって（タイムラインとして）用意する必要がある（`research/B` §2）。つまり **「時刻 t にキャラが何をしていてどこにいるか」を、シミュレーションを回さずに直接計算できる**必要がある。
2. アプリを閉じて数時間後に開いたとき、キャラは「その間も生きていた」場所にいてほしい。連続シミュレーションだと、閉じている間の分を再計算するか、テレポートするかになる。
3. アプリ・ウィジェット・ロック画面（Live Activity）・壁紙セット（§4）が**同じ世界を見ている**ことが「一匹が住んでいる」感の核になる。

**構造**

```
入力:  charaId, personality, room(items), userSeed, 時刻 t（ローカル日付 + 秒）
出力:  SceneState(t) = { activity, position(0..1 正規化), facing, frameIndex, bubble?, targetItem? }

1) DayPlan(date)   = 日付ごとの「日課表」。seed = hash(userSeed, charaId, date)
                     00:00〜24:00 を隙間なく Segment に分割する
                     Segment = { start, end, activity, anchor(アイテム or 座標) }
2) SceneState(t)   = 該当 Segment 内で、t から位置とフレームを O(1) で算出する
```

- **乱数は「連番の PRNG」ではなく「インデックス付きハッシュ」**（`hash64(seed, segmentIndex, waypointIndex)` → SplitMix64 系のミキサ）を使う。これにより任意の時刻の状態を**先頭から再生せずに**求められる（ウィジェットが「30 分後の姿」を即座に描ける）。
- **日課表の生成規則（personality で偏らせる）**
  - 睡眠: 夜型度から就寝 22:00〜01:00 / 起床 06:00〜09:00 を決め、±20 分のゆらぎ
  - 起床直後: stretch → 時計を見る（「おはよう」吹き出し）
  - 覚醒中: 5〜25 分の Segment を、活動度に応じた重みで `wander / idle / sit(item) / nap / play(item) / dance(mirrorBall) / eat / look` から抽選。同じ活動の連続は抑制
  - **時報**: 毎正時の 0〜30 秒は `clockGreet`（立ち止まって正面を向き、時刻の吹き出し）。ケータイパートナーの一次資料では時報機能は未確認だが（`research/A` §5.2）、ガラケー待受文化の定番として採用する
  - ミラーボールが部屋にある場合: 19:00〜23:00 に `dance` の重みを大きく（フワは特に）
  - アイテムの「できること（affordance）」が日課の語彙を増やす: クッション→sit、ベッド→nap/sleep、ボール→play、時計→look
- **wander 内の位置**: 6 秒ごとの経由点 `wp[i] = floor 内の座標（ハッシュで決定）`、`position(t) = easeInOut(lerp(wp[i], wp[i+1], frac))`。経由点で 30% の確率で 2〜6 秒停止（idle フレーム）。`facing` は移動方向の符号。
- **床（floor）**: 部屋ごとに歩ける矩形（正規化座標）と、y に応じた縮尺（奥 0.85 → 手前 1.0）を定義。簡易な 2.5D で「部屋の中を歩いている」感を出す。
- **文脈信号（日課表を上書きする「割り込み」）**: 充電開始→充電器の近くで happy、電池 15% 未満→動きが鈍く昼寝が増える、深夜 1 時以降に画面を見ている→「はやく寝なよ」吹き出し、**3 日以上ぶりにアプリを開いた→喜ぶ**（No Punishment: 罰はなく、ご褒美だけ）。将来: 歩数（Core Motion `CMPedometer`。HealthKit は使わない。D-13。2,000 歩で散歩、5,000 歩で元気、8,000 歩で一緒に喜ぶ。「歩かなかったから悲しい」はやらない）、天気（WeatherKit、Developer Program と Apple Weather 表記が必要。晴れ→散歩、雨→窓を見る、雪→雪を見る）。割り込みは Segment を差し替えるのではなく、`SceneState` の後段で合成するので決定論は保たれる。
- **割り込みの優先順位**（上が勝つ。`260820_gpt.md` §28 を採用）: ① ユーザー操作（将来のタップ・ボタン）→ ② 明示的イベント（充電開始、久しぶりの起動）→ ③ 睡眠（就寝時刻）→ ④ 環境（電池・天気）→ ⑤ 活動（歩数）→ ⑥ 日課表のランダム行動 → ⑦ idle。
- **タップ反応はスコープ外**（メモの指示）。ただし設計上は「割り込み」の一種として後から足せる位置に置いておく。

**テスト（CTCore に集中させる）**: 同一 seed → 同一 DayPlan / 24 時間を隙間・重複なく覆う / 睡眠が指定窓に収まる / 位置が常に floor 内 / Segment 内で位置が連続（テレポートなし）/ アイテムを置くと該当 affordance が使われる / 1 年分（365 日 × 5 キャラ）を回して例外が出ない。ロジックは UIKit に依存させず、`swift test` で数秒で回す。

### 5.5 少ない絵で生きて見せる（プロシージャル動作）

11 枚で「ずっと見ていられる」動きを作るのは、アプリ側の**手続き的な味付け**の役目。すべて「時刻 t の関数」（`sin`、easing、`scaleEffect`/`offset`）として SwiftUI で実装し、絵の追加なしで表情を増やす。状態を持たないので、どの面でも同じ式で同じ姿になる。

| 状態 | 絵 | 味付け |
|---|---|---|
| 歩く | walk×4 ループ（8〜12fps） | 上下に 2〜3pt の bob（sin）、方向転換時に一瞬 squash（xScale 0.9→1.0） |
| 立つ | idle×2 | 3〜7 秒に 1 回まばたき、呼吸で scale 1.00↔1.02 |
| 座る | sit×1 | ときどき首をかしげる（rotation ±4°） |
| 寝る | sleep×2 | ゆっくり呼吸、「z」スプライトが浮かぶ（別レイヤー） |
| 喜ぶ・踊る | happy×2 | 小さくジャンプ、左右に揺れる、ミラーボールの光点（`Canvas` に `.plusLighter` で描く回転光点）とキラキラ粒子 |
| 時報・挨拶 | idle | 吹き出し（SwiftUI テキスト）、正面を向く |
| 影 | なし | 足元の楕円影を別描画。ジャンプで影が小さくなる |

### 5.6 アイテムと部屋

メモの「ミラーボールのようなアイテムを購入して配置」を、**アイテム = 見た目 + キャラの行動の語彙（affordance）+ 演出**として定義する。史実のケータイパートナー／キャラタイムにこの機能はなく（§2.3）、メモの要望に応える新規要素なので、当時の仕様に縛られず iOS の課金（非消耗型）と部屋の表現に合う形で設計する。

| アイテム | affordance | キャラの行動 | 演出 | 導入 |
|---|---|---|---|---|
| ミラーボール | dance | 夜、下で踊る | 回転する光点・キラキラ | Phase 2（象徴アイテム） |
| クッション | sit | 座る・昼寝 | — | Phase 2 |
| ベッド | sleep | 夜はここで寝る | 「z」 | Phase 2 |
| 観葉植物 | look | たまに眺める | 葉が揺れる | Phase 2 |
| 置き時計 | look, clockGreet | 時報で見上げる | 針が実時刻 | Phase 2 |
| ボール | play | 転がして追いかける | — | Phase 4 |
| おやつ | eat（消耗） | 食べる | — | Phase 4 |
| 季節物（こたつ・扇風機・ツリー） | sit/look | 季節限定行動 | — | 将来 |

- アイテムは `items.json` に定義（id, 画像, サイズ, affordance, キャラの立ち位置 anchor, 前後関係）。配置は部屋の床座標。
- **部屋（背景）** は 3 系統: (a) 同梱の部屋イラスト（生成 AI で作る、`research/C` §3）、(b) ユーザーの写真、(c) **ユーザー自身のホーム画面のスクリーンショット**（メモの「アプリが並んでいる画面」を最も直接的に再現する。§4.4）。
- 課金（将来）: アイテムは非消耗型 IAP、おやつ等は消耗型。最初はすべて無料で同梱し、公開判断（Gate 6）後に課金設計を入れる（`research/D` §6）。

### 6.4 後処理パイプライン（`tools/pipeline`、Claude Code が実装）

```
assets-src/characters/piyo/
├─ prompts.md        使ったプロンプトと修正履歴（§6.6 の記録）
├─ sheet.png         参照シート
├─ raw/              生成そのまま（gitignore）
│   ├─ poses.png     8 コマグリッド
│   └─ walk.png      4 コマストリップ
└─ final/            正規化済み（git 管理）
    ├─ piyo_idle_01.png … piyo_walk_04.png   512×512 hero
    └─ mini/                                 256×256
```

```bash
# 1 コマンドで raw → final → Asset Catalog → characters.json → コンタクトシート
python3 tools/pipeline/build.py piyo \
  --poses raw/poses.png --grid 4x2 --map idle_01,idle_02,sit_01,sleep_01,sleep_02,happy_01,happy_02,lookup_01 \
  --walk  raw/walk.png  --grid 4x1 --map walk_01,walk_02,walk_03,walk_04 \
  --chroma auto   # 透明ならそのまま、緑背景なら HSV クロマキー（H≈120°, S>0.6, V>0.5）+ 縁の緑かぶり除去
```

処理内容（Pillow + numpy）: (1) 透明化（`--chroma`）、(2) グリッドを等分割してから各コマの不透明領域で `getbbox()` トリム、(3) 不透明画素の最下端を接地線として揃える、(4) 身長を 400px に正規化（キャラ固有の `scale` は manifest 側）、(5) 512×512 キャンバスに接地線 = 高さ 88% で配置、(6) `mini` 256 を生成、(7) `characters.json` の `poses` を更新、(8) 全キャラ × 全ポーズのコンタクトシート（接地線の補助線付き）を `assets-src/contact_sheet.png` に出力。

ImageMagick が欲しくなる処理（`montage`、`-remap` による減色）は `brew install imagemagick` で後から足す。macOS の「プレビュー → 背景を削除」は少数枚の緊急用。

### 6.6 記録と権利

- **プロンプトと修正履歴を必ず残す**（`prompts.md`）。文化庁「AI と著作権に関する考え方」（2024-03）では、詳細な指示・生成物の確認と修正の反復・加筆修正といった「創作的寄与」があって初めて AI 生成物が著作物になり得るとされる ✅。記録はその主張材料になる（`research/C` §5.2）。
- **AI 出力をそのまま正式採用しない**。輪郭・目・手足・色・特徴パーツ・比率のどれかを人間が意図的に変える（Pixelmator / プレビューでの手直し、または修正指示の反復）。その差分と採用理由も `prompts.md` に残す（`260820_gpt.md` §16〜17 を採用）。
- **類似キャラ調査**を採用前に 1 回行う: Claude に「このデザインから想起される既存キャラは何か」を問い、Google 画像検索で主色 × モチーフ（例: 黄色 ひよこ キャラクター）の上位を目視比較して、識別要素の組合せが一致していないことを確認し、結果を記録する。
- 既存キャラとの「類似性 + 依拠性」があれば侵害。**作風（2 頭身・太線・パステル）は共有してよいが、特定キャラの識別要素の組合せ（口のない白猫 + 赤リボン等）は避ける** ✅。
- OpenAI は出力の権利をユーザーに譲渡、Google はノークレーム ✅。どちらも「AI 生成物を人間が作ったと偽らない」条項があるので、公開時は「キャラは生成 AI を用いて制作」と明記する。Gemini の出力には不可視の SynthID が入る（問題なし）。
- 生成元の raw 画像は git に入れない（容量と、万一の差し替え容易性）。

### 6.7 将来の UGC（ユーザーのオリジナルキャラ）

**段階 1（Phase 5、API なし・費用ゼロ）**: アプリが「キャラの説明を入れると §6.3 のプロンプトを組み立ててコピーする」→ ユーザーが自分の ChatGPT / Gemini で生成 → 画像（1〜12 枚）をアプリに取り込む → 端末内で Vision（`VNGenerateForegroundInstanceMaskRequest`）が被写体を切り抜き → §6.4 と同じ正規化を Swift で実行 → ポーズを割り当て（1 枚だけなら Tier 0） → 登録。**審査上も UGC のモデレーション要件（1.2）が軽い**（端末内に閉じ、他人に見せない）。

**段階 2（将来、アプリ内生成）**: 自社バックエンド経由で `gpt-image-2.5-flare`（透明出力・`moderation` パラメータ）を呼ぶ。1 体（シート 1 + ポーズ 8 + 歩行 4 + リトライ 3 割）で **約 $0.5〜1.8** 🔷。コスト最優先なら `gemini-3.1-flash-lite-image`（約 $0.034/枚 ✅）+ クロマキー。設計要件: API キーをアプリに埋め込まない、入力は構造化フォーム（色・生き物・持ち物・性格）に限定して STYLE LOCK と結合、禁止語ブロック、Claude Vision で IP 類似・NSFW 判定、通報・ブロック・削除（App Store 1.2）、「AI 生成」表示、日次上限と Batch（Gemini は 50% off）。Apple の Image Playground はオンデバイス無料だが、`ImageCreator` が iOS 27 で deprecated ✅ で、参照ポーズ生成もできないためスプライト用途には使わない。**前例**: SpritePals は写真を Cloudflare Worker → OpenAI に中継して生成し（端末側は動物判定のみ）、生成トークン課金（1 回 $0.99〜）で原価を回収、年齢区分 4+ で審査を通過している ✅（`research/F` §1）。ただし「毎回有料」が最大の不満なので、CharaTime は段階 1（端末内・無料）を先に出し、段階 2 は Pro 買い切りに生成回数を同梱する形を検討する。

### 7.4 データモデル（骨子）

```swift
// CTCore（純 Swift）
public struct Personality: Codable, Sendable {
    public var activity: Double        // 0..1  歩き回る頻度
    public var nightOwl: Double        // 0..1  夜型度（就寝・起床の窓を決める）
    public var napiness: Double        // 0..1  昼寝の頻度
    public var favorites: [ItemKind]   // 重み付けに使う
}

public struct Character: Codable, Sendable, Identifiable {
    public let id: String              // "piyo"
    public var displayName: String
    public var scale: Double           // 体格差。1.0 = 身長 400px 基準
    public var personality: Personality
    public var poses: [Pose: [String]] // .walk → ["piyo_walk_01", ...]
    public var origin: Origin          // .bundled / .user(createdAt:)
}

public struct Room: Codable, Sendable {
    public var background: Background  // .bundled(id) / .photo(fileName) / .homeScreenShot(fileName)
    public var floor: CGRect           // 正規化座標（0..1）
    public var depthScale: ClosedRange<Double> // 奥 0.85 ... 手前 1.0
    public var items: [PlacedItem]     // { itemId, position(0..1), zHint }
}

public struct ContextSnapshot: Codable, Sendable { // 本体アプリが App Group に書く文脈キャッシュ
    public var batteryLevel: Double?; public var isCharging: Bool?; public var capturedAt: Date
}

public struct WorldInput: Sendable {  // すべての面が同じ入力を組み立てる
    public let character: Character
    public let room: Room
    public let userSeed: UInt64
    public let context: ContextSnapshot?
    public let calendar: Calendar      // ローカルタイムゾーン
}

public struct SceneState: Equatable, Sendable {
    public let time: Date
    public let activity: Activity      // .sleep / .wander / .idle / .sit(itemId) / .dance(itemId) / .clockGreet ...
    public let position: CGPoint       // 正規化
    public let facing: Facing          // .left / .right / .front / .back
    public let frame: Int              // 表示フレーム index
    public let bubble: Bubble?         // 「おはよう」「12:00」など
}

public func sceneState(at t: Date, input: WorldInput) -> SceneState
public func dayPlan(for date: DateComponents, input: WorldInput) -> DayPlan
```

- `state.json`（CTStore）: `schemaVersion`, `selectedCharacterId`, `room`, `userSeed`, `context`, `widgetCrops: [slot: fileName]`, `settings`（時計表示、夜モード、音）。**スキーマにバージョン番号を持たせ、後方互換の読み込みを最初から書く**（ウィジェットとアプリで別ビルドが混在し得る）。
- UGC キャラ（Phase 5）は同じ `Character` 型に `origin: .user` で追加し、画像は App Group の `images/` に置く。同梱キャラと同じ経路で描画される。
- **Segment の境界は 5 分グリッドに揃える**。ウィジェットのエントリ（5 分刻み）と境界が常に一致し、「ウィジェットで見た姿」と「直後にアプリを開いた姿」がずれない。毎正時の時報（0〜30 秒）は :00 のエントリが担う。

### 7.5 描画（CTRender）

**共通**: `SceneView(state: SceneState, date: Date, room: Room, mode: RenderMode)` が 1 枚の絵を描く。

```
ZStack
 ├─ 背景（部屋イラスト / 写真 / ホーム画面スクショ / 透過用切り抜き）
 ├─ 奥のアイテム（y でソート）
 ├─ 影（Ellipse、ジャンプで縮小）
 ├─ キャラ（Image(mini or hero) .scaleEffect(x: facing == .right ? -1 : 1) .scaleEffect(character.scale × depthScale(y)) .offset(bob)）
 ├─ 手前のアイテム
 ├─ 効果（Canvas: ミラーボールの光点・キラキラ。mode が .widget なら省略）
 └─ 吹き出し・時計（SwiftUI テキスト）
```

**アプリ内（待受モード）**: `TimelineView(.animation) { ctx in SceneView(state: sceneState(at: ctx.date, ...), date: ctx.date, ...) }`。プロシージャル味付け（§5.5）は `ctx.date` の関数として計算する（`sin`、easing）ので、アニメーション状態を持たない = 復帰時の不整合が起きない。位置は前フレームとの距離が閾値以上なら即時、それ以外は補間。静止・睡眠中は `TimelineView(.periodic(from:by: 1/30))` に切り替えて負荷を落とし、画面が見えないときは描画を止める。`isIdleTimerDisabled` は待受モード表示中のみ true。

**ウィジェット**: `SceneView(state: entry.state, date: entry.date, mode: .widget(family, renderingMode))` を静的に描く。

- タイムライン: 現在から 4〜6 時間先まで **5 分刻み（48〜72 エントリ、公式の「エントリは約 5 分以上離す」に整合 ✅）** + 毎正時、`.atEnd` で再読込。1 日の再読込は 4〜6 回で、予算（頻繁に見られるウィジェットで 1 日 40〜70 回 ✅）に大きな余裕を残す。
- **描画モード** ✅（`research/E` §2.1）: ホーム画面がフルカラーなら通常、iOS 26 の「クリア / ティント」外観では **accented**（内容が単色化）→ キャラ画像に `.widgetAccentedRenderingMode(.fullColor)` を付けて色を保つ（要実機確認）。ロック画面は **vibrant**（脱色モノクロ）、StandBy の夜間は赤ティント → **シルエットで誰か分かる**キャラデザイン（§5.1 の「1 つだけ特徴的な突起」）がここで効く。
- `containerBackground(for: .widget)` を使い、StandBy / ロック画面では背景が取り除かれても成立する構成にする。
- 「キャラが本物の壁紙の上にいる」見せ方（透過ウィジェット）は §4.4。
- **1〜8fps の疑似アニメ**（`Text(timerInterval:)` + マスク用カスタムフォント、Bryce Bostwick が 2025-05 に公開 API のみで実証 ✅）は Phase 0 のスパイクで実機判定し、Go なら Phase 3 で組み込む。フォントは fontTools で自動生成できる（`research/E` §2.3）。

**描画能力の段階とフォールバック（RenderCapability）** — `260820_gpt.md` §4.5・§9・§10 を採用。アニメの実装方法を View に直書きせず、能力レベルで切り替える。

```swift
public enum RenderCapability: Int, Comparable {   // 大きいほど高機能。失敗したら 1 段下へ
    case staticOnly = 0        // 静止画 1 枚（最後の砦。ここまでは必ず動く）
    case timelineTransition    // 5 分ごとの静止画 + エントリ切替の 2 秒トランジション（Apple 公式の方式）
    case ambient1fps           // Text(timerInterval:) + マスクフォントで 1fps（まばたき・呼吸）
    case ambient4fps           // 複数タイマーの位相ずらしで 2〜4fps（歩行）
}
```

- 面ごとの既定: 待受モード = SwiftUI 60fps（この梯子の外）、ウィジェット = スパイクの結果で `ambient1fps` または `timelineTransition`、ロック画面・常時表示 = `timelineTransition`（減光時はアニメが行われない ✅）、Live Activity = スパイク結果に準じる。
- 判定は「OS バージョン × feature flag × ユーザー設定（省電力・Reduce Motion）」で決め、**未知の OS では `timelineTransition` に落とす**。iOS の更新でハックが止まっても、キャラは静止画で必ず表示される（「キャラが消えた」だけは起こさない）。`ambient1fps` 以上は「Xcode 26.1 以降の SDK でビルドすると止まる」という報告がある（`research/F` §2）ため、Phase 0 のスパイクで実機判定するまで既定にしない。
- `accessibilityReduceMotion` が ON なら bob・跳ねを止め、フレーム切替だけにする。

**ウィジェットの確認**: シミュレータのホーム画面にウィジェットを一度置く（手動、初回のみ。シミュレータの状態は保持される）→ 以後は `xcrun simctl io booted screenshot` でホーム画面ごと撮れる。ウィジェットのタイムラインを強制更新するには、アプリ側のデバッグメニューから `reloadAllTimelines()` を叩く。`#Preview(as:)` で 3 サイズを並べて確認する方が速い場面も多い。

### 8.4 実機

- 無料の Personal Team で署名した場合は 7 日で失効（TrainNow §7.4 と同じ手順）。Phase 3 でウィジェットを常用し始めたら Developer Program に切り替える。
- **iOS 26 に据え置く（v1.2 の決定 D-15）**: macOS 26.5.2 を上げないため Xcode 27（macOS 26.6 以上が必須 ✅）は入れられない。したがって **Xcode 26.6（iOS 26.5 SDK）+ 実機 iOS 26.1** の組み合わせで Phase 3 まで進める。deployment target は 26.0 のまま。
- **この構成で困らない理由**: (1) Phase 0〜3 で触る API（WidgetKit のタイムライン・`containerBackground`・accented / vibrant レンダリング・App Group・StandBy・`Text(timerInterval:)`）はすべて iOS 26 にある ✅。(2) Liquid Glass とクリア／着色外観は **iOS 26 で導入済み**なので、透過ウィジェットの成立条件の検証は iOS 26 で正しくできる ✅。(3) iOS 27 の新要素（`systemExtraLargePortrait`、Dynamic Island の横向き、StandBy の `activityBackgroundTint`、`LiveActivityIntent`、Watch / Mac / CarPlay への自動転送）はすべて Phase 4 以降の装飾で、**ウィジェットのアニメーション制約は iOS 27 でも変わらない** ✅（`research/B` §1）。
- **むしろ iOS 26.1 の実機はスパイクに好都合**: 疑似アニメが壊れる条件は「**Xcode 26.1 以降の SDK でビルドしたバイナリを iOS 26.1 以降で動かす**」と報告されている 🔶（`research/F` §2）。手元は Xcode 26.6（SDK 26.5）× 実機 iOS 26.1 なので、**すでにその条件を満たしている**。つまり Phase 0 のスパイクは「延命策なしの現実的な条件」をそのまま測ることになり、判定に意味がある。
- **据え置きで失うもの（すべて Phase 4 以降）**: iOS 27 実機での見え方の確認、上の新 API の実装と検証。公開する場合、Apple は例年、主要 OS 公開から数ヶ月後に最新 SDK でのビルドを提出要件にする 🔷（要確認）。Gate 6（11/30）には影響しないが、実際に App Store へ出す段になったら macOS と Xcode を上げる必要が出る。
- **やってはいけないこと**: iPhone を iOS 27 に上げること。上げた瞬間に Xcode 26.6 から実機へインストールできなくなり、macOS 更新（約 1 時間）+ Xcode 27 ダウンロード（15〜20 GB）を挟むまで実機検証が止まる。**9/14 の公開前に自動アップデートを切る**（R-6）。iOS 26.x 内の小数点更新も、Phase 3 が終わるまでは見送るのが安全。
- **メモリ 8 GB での回し方（v1.2 追加。スワップ 12.8 GB 使用中の実測を踏まえる）**: Xcode.app は常時開かず `xcodebuild` CLI とスクリプトで回す / シミュレータは同時 1 台（未使用の 9 台は削除）/ ロジックは `swift test`（数秒・軽い）で検証し、アプリのビルドは必要なときだけ / ビルド中は Chrome と Docker を閉じる / DerivedData は `ios/build` に固定して定期的に消す。**この機械の事情が、CTCore を UI 非依存の純 Swift にしてテストを主戦場にするという §7.3 の判断を裏づけている**。

**本番のウィジェット拡張とは別のターゲットにした**（`app.charatime.spike`）。

どのウィジェットにも 2 つの読みを出してある。**秒のカウンタ**（OS が描き直しているか）と

#### Phase 0 の判定（2026-09-23 セッション 6・0-9a〜0-11）

**Conditional Go で確定した**（D-11、Q-12）。記録は `docs/260912_spike.md` §4。

| 見たもの | 結果 |
|---|---|
| **C**（マスク書体で 1fps） | **一度も点かない。** 不安定なのではなく最初から動かない |
| **D**（4fps） | **丸が 1 つも出ない。** C と同じ細工の上に乗っているため |
| **B**（エントリ切替） | **1 分ごとに ● が 1 つ進む。** 公式の目安（5 分以上）より細かい刻みでも拾われた |
| **秒カウンタ**（A〜D 共通） | **すべて進む。** 拡張が動いていないあいだも画面は更新されている |

**`research/F` §2 の読みを実測で訂正した。** 報告は「Xcode 26.1 以降の SDK で止まる」と
しか言っておらず、何が止まるかは書かれていなかった。こちらは「拡張が止まっているあいだの
**描き直し**が止まる」と読んでいたが、逆だった。止まったのは
**タイマー文字にカスタム書体を当てる細工**のほうで、描き直しそのものは生きている。

**この区別が Phase 3 に効く。** 土台が生きているので、`Text(timerInterval:)` を
**素の文字として使う**見せ方（セッションの残り時間・秒まで出る時計）は面 1 でも面 3 でも
使える。失われたのは「絵を毎秒出し入れする」細工だけである。

B が 1 分刻みでも拾われたことは、§7.5 の「5 分刻み × 4〜6 時間を事前計算し、
再読込は 1 日 4〜6 回」という設計が予算に対して余裕を持つことを裏づける。
ただし見たのは置いた直後の数分なので、**粘りは 3-7（1 週間の実機運用）で測る**（R-2）。

スパイクのターゲットは**まだ消さない**。本番と違う設定（1 分刻み）なので延命しても
実にならないが、Phase 3 の 3-2 に入るまでは比較対象として残す。

#### 判定の見直し（2026-09-23 セッション 6 の続き・スパイク E）

**判定を Conditional Go の暫定に戻した。** C・D が点かなかった原因を、スパイク E で切り分けた。
シミュレータのホーム画面（iOS 26.5）に E と元の C を並べて置き、WidgetKit が実際に描いた姿を
連続撮影して画素で数えた（`docs/260912_spike.md` 3-6）。

- **原因はこちらの組み方だった。** タイマー文字に当てた `.fixedSize()` が、ウィジェットの中では
  枠の幅を有限の値にしない。字は描かれず、右端 1em を切り出しても何も無い
- **枠の幅を決めて右寄せにすれば描かれる。** 組み直した α は 1 秒ごとに点滅し、δ は 1 秒に 4 回変わった。
  そのあいだ拡張は動いていない（「絵を作ったのは」の時刻が変わらない）
- **シミュレータは実機の失敗を再現していた。** 元の C は、実機と同じく「薄い丸が 2 つ」だけ

実機で E の α（か γ）が点けば Go の候補になり、3-4 のマトリクスを E で測り直して確定する。
α・γ・δ は丸 1 日数え続けるので、「1 時間放置」も測れる。

**→ 実機（iPhone 17 Pro / iOS 26.1）でも同じ結果になった（2026-09-23 15:32）。** α と γ は 1 秒ごとに
入れ替わり、δ も形を変えた。拡張は動いていない。**判定は Go の候補**で、残りはマトリクス。

### Phase 7 以降の候補（13 週の外。優先順）

1. **発言生成**（D-12）: 吹き出しの文言をテンプレートから、性格（おだやか / 好奇心 / 元気 / 内気 / いたずら）× 文脈（時刻・天気・歩数・久しぶり）で **Apple Foundation Models（オンデバイス）** に生成させる。生成は本体アプリの前景で行い、翌日分の候補（時間帯 × 状況で 30〜50 本）を App Group にキャッシュしてウィジェットが表示する（拡張内の生成は Apple 非推奨 ✅）。Instructions は英語で「The person's locale is ja_JP. You MUST respond in Japanese.」、`@Generable` で `{ utterance: String }` だけを返させ、文脈 4,096 トークン（日本語は 1 文字 ≈ 1 トークン）に収める。可用性 5 分岐でテンプレートに戻す。行動は引き続き決定論エンジン。短い構造化メモリ（名前、好きな話題、直近の出来事 3 件）を端末内に保持。クラウド LLM は「明示的に説明・同意」の上でのみ（`research/F` §3）。
2. **タップ・ボタン反応**（メモで後回しにした分）: ウィジェットの `Button`（AppIntent、再読込は予算外 ✅）と待受モードのタップ。
3. **状態のバックアップ**: Pixel Pals の最大の不満は同期なしによる進捗消失（`research/D` §1.4）。iCloud KVS か「書き出し / 読み込み」で `state.json` と UGC 画像を守る。
4. Apple Watch の Live Activity / Smart Stack、Mac メニューバー（iOS 26 で自動転送 ✅）の見え方調整。
5. 季節イベントの配信（アプリ更新で同梱）、ドット絵パック、Rive による待受モードのなめらか化。
