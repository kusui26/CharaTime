# Ambient Character iOS App — Development Plan

> 最終更新: 2026-08-20
> 対象: iPhone / iOS 26以降を主対象
> 開発方式: Native iOS / Swift / SwiftUI
> 仮コンセプト: **「iPhoneの中に、小さなキャラクターが住んでいる」**

---

# 1. Executive Summary

## 1.1 このアプリで実現したいこと

iPhoneのホーム画面を見ると、小さなキャラクターが、

* 歩く
* 立ち止まる
* まばたきする
* 座る
* 寝る
* 起きる
* 食べる
* 喜ぶ
* ときどきこちらを見る

などの行動を、ユーザーが毎回操作しなくても行っている。

ユーザーがタップすると、

* 撫でる
* 餌をあげる
* 遊ぶ
* 話しかける

といったリアクションを返す。

さらに将来的には、

* 時刻
* 曜日
* 天気
* 歩数
* 過去のやり取り
* キャラクターの性格
* ユーザーとの親密度

などによって行動や発言が変わり、

> **「Widgetを表示している」のではなく、「iPhoneの中に何かが住んでいる」**

と感じられる体験を目指す。

# 3. 既存サービスとの差別化

現在の代表的な競合として、Pixel Pals と SpritePals がある。

Pixel PalsはHome Screen / Lock Screen / Live Activitiesにピクセルペットを表示し、Virtual Pet、ゲーム、農業、Morph、友達との交流など幅広い機能を持っている。

SpritePalsは、ユーザー自身の犬や猫などの写真をAIでPixel Pet化し、Home Screen、Dynamic Island、Lock Screen、Apple Watchへ展開することを特徴としている。

本アプリでは、これらと真正面から「ペットゲームの機能数」で競争しない。

## 差別化の中心

### Pixel Pals

> Virtual Pet / Widget Game

### SpritePals

> Your Pet → AI Pixel Pet

### 本アプリ

> **Ambient AI Character / Living Character**

つまり、

**「育成ゲーム」よりも「存在感」**

を中心に置く。

キャラクターが何かを要求してくるアプリではなく、

> ホーム画面を見る
> ↓
> 「あ、寝てる」
> ↓
> しばらくして見る
> ↓
> 「今度は歩いてる」
> ↓
> タップする
> ↓
> こちらを見て反応する

という体験そのものをプロダクトの核にする。

# 4. プロダクト設計の原則

## 4.1 Ambient First

キャラクターはユーザーがアプリを開いていなくても「存在している」ように感じられること。

ゲーム画面を開かないと成立しない体験にはしない。

---

## 4.2 Glanceable

1〜2秒ホーム画面を見るだけで、

* 今何をしているか
* どんな気分か

が分かる。

WidgetKit自体も「glanceable」な体験を前提として設計されている。

---

## 4.3 No Punishment

昔の育成ゲームのように、

* 数日放置すると死ぬ
* 世話しないと病気になる
* 通知で何度も世話を要求する

という設計にはしない。

むしろ、

> 久しぶりに見たら嬉しそうにしている

くらいの優しい設計にする。

---

## 4.4 Local First

可能な限り、

* キャラクター状態
* 会話
* 記憶
* AI処理

をiPhone内で完結させる。

MVPではアカウント登録もバックエンドも不要とする。

---

## 4.5 Graceful Degradation

アニメーションの特殊な実装がOS更新で動かなくなっても、

**キャラクターそのものが消えない設計**

にする。

常に、

```text
高速アニメーション
       ↓ 失敗
低fpsアニメーション
       ↓ 失敗
状態変化＋2秒アニメーション
       ↓
静止キャラクター
```

までフォールバックできるようにする。

---

# 5. 技術調査から得られた最重要事項

## 5.1 Widget Extensionは常時動作しない

Widget Extensionがバックグラウンドで毎秒コードを実行することはできない。

一方でAppleは、`Text(date, style: .timer)`のような一部のSwiftUI Viewについては、Widget Extensionが実行されていなくても、Widgetが表示されている間OS側が継続的に表示を更新すると明記している。

---

## 5.2 通常のWidgetアニメーションは最大2秒

SwiftUIによるWidget / Live Activityの通常アニメーションは最大2秒。

したがって、

```swift
.animation(.linear(duration: 60))
```

のような方法で、60秒間キャラクターを歩かせ続ける設計にはしない。

---

## 5.3 Timer表示を「アニメーションクロック」として利用するPoCが存在する

Bryce Bostwick氏の公開PoCでは、

* 公開APIのみ
* Widget内
* 30秒ループ
* 8fps
* 同じ方式で最大30fps

のアニメーションを実現している。

基本アイデアは、

```text
Text(.timer)

00
01
02
03
...
```

を、カスタムフォント等によって、

```text
frame 00
frame 01
frame 02
frame 03
...
```

として扱うこと。

---

## 5.4 ただしOS依存リスクがある

上記PoCについては、iOS 26.2で動作しなくなったというIssueも公開されている。

したがって、

> 「30fpsで常時動くこと」

をプロダクト成立の絶対条件にしてはいけない。

## 8.5 Prototype E — 2〜4fps

# 9. Animation Engine Architecture

アニメーション方法をViewへ直接書き込まない。

以下の抽象化を設ける。

```swift
protocol CharacterAnimationRenderer {
    func render(
        animation: CharacterAnimation,
        startDate: Date
    ) -> AnyView
}
```

実装を分ける。

```text
CharacterAnimationRenderer
│
├── StaticRenderer
│
├── TimelineAnimationRenderer
│
├── TimerGlyphRenderer
│
└── ExperimentalHighFPSRenderer
```

# 10. Animation Capability Level

内部的に以下を持つ。

```swift
enum AnimationCapability {
    case staticOnly
    case standard
    case ambient1fps
    case ambient4fps
}
```

例えば、

```text
iOS A
→ ambient4fps

iOS B
→ ambient1fps

未知OS
→ standard
```

と切り替えられる構造にする。

**OSアップデートで特殊実装が壊れても、アプリ全体を壊さない。**

# 15. Emojiを正式キャラクターにしない理由

Unicodeの「🐶」という文字コード自体と、Appleが描いた🐶のグラフィックは別物。

Unicode Consortium自身も、各ベンダーのカラーEmoji画像について、著作権・商標等は各権利者に帰属すると明記している。

AppleもApple画像・Emoji等をモバイルアプリで使用する場合の権利問い合わせ窓口を用意している。

したがって、

```text
🐶をTextとしてプロトタイプ利用
```

は便利だが、

```text
Apple Emojiを画像化
↓
加工
↓
正式マスコット
```

という設計にはしない。

```yaml

  origin: "lives inside a smartphone"
  personality:
    - curious

  silhouette: simple
  limbs: short

  colors: 2-4
  style: pixel-friendly

  readable_at_24px: true
  readable_at_40px: true
  side_view_possible: true
```

---

## Step 2 — AI Concept Generation

AIで20〜50案程度出す。

ただし、

```text
「たまごっち風」
「ポケモン風」
「サンリオ風」
```

文化庁のガイダンスでも、生成時に既存作品名やキャラクター名など特定の固有名詞を入力した事実は、既存著作物への依拠性を判断する上で問題となり得るため、生成過程を記録しておくことが推奨されている。

## Step 3 — Human Redesign

AI画像をそのまま正式採用しない。

* 輪郭
* 目
* 手足
* 色
* 表情
* 特徴的パーツ
* 比率

を意図的に変更する。

文化庁は、AI生成物について人間に「創作意図」と「創作的寄与」が認められる場合には著作物となり得ると説明している。

# 20. アセット制作方針

Pixel Artを基本とする。

理由:

* 小さなWidgetで識別しやすい
* 低fpsでも違和感が少ない
* アニメーションFrame数を抑えられる
* レトロ待受キャラとの相性が良い
* Asset容量を小さくできる

Master Spriteは、

```text
32×32
または
48×48
```

程度から検証する。

表示時は整数倍率を基本とし、pixelated appearanceを維持する。

# 24. App Group設計

# 25. Shared Data

軽量な最新状態は、

```text
UserDefaults(suiteName: appGroupID)
```

に保存する。

大きな履歴データはMain App側に保持する。

Widgetには必要なSnapshotだけ渡す。

```text
Main Database
      │
      ▼
 PetSnapshot
      │
      ▼
 App Group
      │
      ▼
 Widget
```

この構成なら、Widget Extension側が複雑なDB migrationへ依存しない。

# 27. Character Behavior Engine

AIにキャラクター行動を全部決めさせない。

基本行動は**決定論的なState Machine**で決める。

```text
Input
│
├── Current Time
├── Previous State
├── Interaction
├── Activity
└── Environment
│
▼
Behavior Engine
│
▼
Current Behavior
```

---

# 28. 行動Priority

```text
1. User Interaction
2. Explicit Event
3. Sleep
4. Environment
5. Activity
6. Random Ambient Behavior
7. Idle
```

例えば、

```text
ユーザーが餌を押す
        ↓
Eating

22:30
        ↓
Sleeping

雨
        ↓
Umbrella

その他
        ↓
Walking / Sitting / Idle
```

# 29. Randomnessの設計

毎回完全randomにはしない。

例えば、

```swift
seed =
    characterID
    + date
    + fifteenMinuteBucket
```

のようなSeeded Randomを利用する。

これにより、

```text
Widget reload
↓
毎回違う場所に瞬間移動
```

という問題を防ぐ。

# 34. Dynamic Island

Dynamic Islandは**常時常駐ペットとして使用しない。**

AppleはLive Activitiesについて、開始と終了が明確な短〜中時間のイベント・タスクに使用することを推奨している。

さらにLive Activityは最大8時間で自動終了し、Dynamic Islandから削除される。Lock Screenには最大4時間追加で残る。

したがって、

```text
24時間365日Dynamic Island Pet
```

を無理に実装しない。

---

# 35. Dynamic Islandの正しい使い方

例えば、

## 「いっしょに過ごす」

というモードを作る。

```text
いっしょに過ごす
  1時間
  2時間
  4時間
```

開始すると、

```text
        Character
           ↓
━━━━━━━━━━━━━━━━━
   Dynamic Island
```

に出現。

一定時間経つと、

```text
「またあとでね」
```

として終了。

これならLive Activity本来の、

> 明確な開始と終了

にも合う。

# 37. AIの最初の用途

AIには行動制御ではなく、

**発言生成**

だけを担当させる。

例えばState Engineから、

```json

  "mood": "happy",
  "time": "morning",
  "weather": "sunny",
  "steps": 4210,
  "lastInteraction": "yesterday"
}
```

を渡す。

AIは、

```json
{
  "utterance": "今日はどこ行く？"
}
```

だけ返す。

# 38. なぜAIに行動制御をさせないか

LLMに、

```text

餌を食べる
```

* 非決定的
* 遅い
* OS Widget更新と相性が悪い
* オフラインで壊れる
* API障害でキャラが止まる

という問題がある。

したがって、

```text

→ 行動

LLM
→ Personality / Dialogue
```

と分離する。

# 76. 開発方針の最終結論

このプロジェクトでは、以下を守る。

1. **Home Screen Widgetをプロダクトの中心にする**
2. **最初にAmbient Animationの実機PoCを完成させる**
3. **30fpsを追わず、1〜4fpsのPixel Animationを狙う**
4. **特殊アニメーション方式は必ずFallback可能にする**
5. **Private APIには依存しない**
6. **Dynamic Islandは期間限定Companion Sessionとして使う**
7. **正式キャラクターはオリジナルIPにする**
8. **Emojiはプロトタイプ用途に限定する**
9. **AI画像をそのまま正式キャラクターにせず、人間が十分に創作・修正する**
10. **MVPではバックエンドを作らない**
11. **行動はState Machine、会話はAIという責務分離を行う**
12. **AIはプロダクト価値が確認されてから追加する**
13. **iOS 26だけでなくiOS 27でも継続的に実機検証する**
14. **機能数ではなく「存在感」を最優先する**
