# ウィジェット疑似アニメ 実機スパイク

プラン `260910_dev_plan.md` §9 Phase 0 の 0-9〜0-11。判定は同 §12 の **D-11** に記録する。

作成 2026-09-12 / 判定 **Go**（2026-09-23 確定。§4 に記録）

面 1 は「**動く窓**」になる。拡張が止まっていても、ホーム画面のウィジェットの絵を
1 秒ごと（`ambient1fps`）、さらに 1 秒に 4 回（`ambient4fps`）まで入れ替えられる。

**経緯**: 2026-09-23 に一度 Conditional Go と記録したが、C・D が点かなかったのは手法ではなく
こちらの組み方（`.fixedSize()`）のせいだった。スパイク E（3-6）で切り分け、組み直した α が
実機（iOS 26.1）で**ロック解除後も kill 後も**点き続けたので Go に上げた。画面収録では、
1 秒の点滅と 4fps をコマ単位で確かめた。

**Phase 3 の 3-0 で F・G を足した**（2026-09-23、3-7）。本番の組み方（0 時起点・数字の集まり・入れ子の「かつ」・
エントリ切替）とタイマーの本数、背景を透明にしたときの見え方を、シミュレータと実機で測った。
**実機では、14 本のウィジェットでも、ホーム画面に戻った直後に止まらなかった**（E の「約 1 秒」は収録の開始直後だけの現象）。

## 1. 何を決めるためのものか

ホーム画面のウィジェットを「動く窓」にできるか、「様子が変わる窓」に留めるかを決める。

iOS のウィジェット拡張は自分では動けない。1 日 40〜70 回の更新予算があるだけで、
秒単位の描画はできない。ただ `Text(timerInterval:)` だけは
**拡張が止まっていても OS が毎秒描き直す**。そこにカスタムフォントを当てて
絵をマスクすると、絵が毎秒出たり消えたりする。

これは **Apple が保証した手法ではない**。Bryce Bostwick が 2025-05 に公開 API のみで
実証したが（`research/E` §2.3、`research/F` §2）、

- Apple がいつ塞いでもおかしくない（Hackaday「don't expect it to work forever」）
- **Xcode 26.1 以降の SDK でビルドすると止まる**という報告が複数ある

ので、**手元の実機で確かめてから決める**。

### 手元の構成で測る意味

プランの 0-9 は当初「Xcode 27 でビルド、iOS 27 実機」と書いていたが、
D-15 で **macOS 26.5.2 / Xcode 26.6 / iPhone 17 Pro iOS 26.1 の据え置き**を決めた。

**この構成は、止まるという報告の条件（Xcode 26.1 以降の SDK）を既に満たしている。**
つまりここで動けば手元では使えるし、動かなければ手元では使えない。
Phase 3 まではこの構成で開発するので、**測るべきはこの構成**である。

## 2. 入れるもの

5 つのウィジェットを用意した。**本番のウィジェットとは別のターゲット**
（`app.charatime.spike`）なので、ここで何が起きても本番は巻き添えにならない。

| | 何 | 見るところ | 位置づけ |
|---|---|---|---|
| **A** | 静止した ● | 動かない | ほかを比べるための基準 |
| **B** | エントリ切替で ● が 1 分ごとに進む | ● が進むか | **Apple 公式の方式。最後の砦** |
| **C** | マスクフォントで 1 秒ごとの点滅 | 左 2 つが交互に点くか | 非公式。**判定の分かれ目** |
| **D** | 0.25 秒ずらした 4 本で 4fps | 点いている ● の数が増減するか | 非公式。C が動いてから見る |
| **E** | C・D が点かなかった理由の切り分け（大） | 8 行（3-6） | 2026-09-23 追加。**α〜δ が C・D の直した版** |
| **F** | 本番の組み方の確かめ（小 6 枚＋大 1 枚） | 3-7 | Phase 3 の 3-0b。タイマーの本数、0 時起点、かつ、エントリ切替 |
| **G** | 背景を透明にしたときの見え方（小 3 枚） | 3-7 | Phase 3 の 3-0c。壁紙が透けるか |

どのウィジェットにも **2 つの読み**を出してある。ここがいちばん大事。

- **表題の横の秒のカウンタ**: `Text(timerInterval:)` をそのまま出したもの。
  **これが進んでいれば、OS はウィジェットを描き直している。**
- **下段の「絵を作ったのは hh:mm:ss」**: タイムラインのエントリが作られた時刻。
  **秒のカウンタが進んでいるのにこちらが古いままなら、
  拡張が動いていないのに画面だけ更新されている。** それがこの手法の要。

## 3. 手順

### 3-1. 先に 5 分だけ（0-9a）

App Store の **Pixel Pals** と **秒時計 for Widget** を入れて、
ホーム画面のウィジェットが秒単位で動くかを見る。

- 動く → C・D にも期待できる
- 動かない → C・D の期待値を最初から下げてよい（判定が早く終わる）

**所見（2026-09-22、iPhone 17 Pro / iOS 26.1）:
ロック画面と Dynamic Island では動いていた。ホーム画面は測っていない。**

| 見たところ | 面 | 秒が進んでいるか |
|---|---|---|
| ロック画面ウィジェット「22:44:27」（秒時計） | 面 1 と同じ WidgetKit | **進んでいる**。本体のロック画面時計は 22:44 で秒を出さないのに、ウィジェットは `:27` を出している |
| Dynamic Island の丸「38」（秒時計） | 面 3 | **進んでいる**。上の `:27` の 11 秒後で、分は同じ 22:44 |
| ロック画面ウィジェット「Hugo the Cat」（Pixel Pals） | 面 1 と同じ WidgetKit | 静止画からは判断できない |
| Dynamic Island の猫（Pixel Pals） | 面 3 | 同上。Pixel Pals の売りはここで、**面 1 の証拠にはならない** |

**これで分かったこと。** `Text(timerInterval:)` 系の文字は、iOS 26.1 の実機で
**ウィジェットの面でも毎秒描き直されている**。C が乗ろうとしている土台は生きている。

このときホーム画面には両アプリのウィジェットを置いていなかったので、
**ホーム画面は測れていなかった**（アイコンが並んでいるだけ。ウィジェットは手で置くもので、
アプリを入れただけでは出ない）。

**追記（2026-09-23）: ホーム画面も測った。動いていた。** 秒時計も、スパイク A〜D の
秒カウンタも、ホーム画面で秒を刻んだ。**上の分岐は「動く → C・D にも期待できる」の側**で
確定する。詳しくは 3-4。

### 3-2. アプリを入れる

`scripts/ios-device.sh --install` で、ビルドから起動まで 1 コマンドで入る。
スパイクのウィジェット拡張はアプリに同梱されるので、別の操作は要らない。

```bash
scripts/ios-device.sh --install                  # 入れて待受モードで開く
scripts/ios-device.sh --install --screen spike   # 入れて下見画面で開く
```

初回だけ `.env.local` に署名の Team ID が要る（`.env.local.example` をコピーする）。
**Xcode.app は開かない。** メモリ 8 GB の機械では、開かないことがそのまま速さになる。

**無料アカウントの署名は 7 日で切れる。** 切れたら入れ直す。

### 3-3. ウィジェットを置く

**アプリを入れただけではウィジェットは出ない。** 1 枚ずつ手で置く。
Live Activity（Dynamic Island）とロック画面ウィジェットは別枠で、
そちらが見えていてもホーム画面には何も出ない。

1. ホーム画面の**何もないところ**を長押しする（アイコンが揺れ出す）
2. **左上の「編集」** → **「ウィジェットを追加」**
3. 上の**検索欄にアプリ名**を入れ、出てきたアプリをタップする
4. 見本を**左右にスワイプ**して目当てのウィジェットを出し、**「ウィジェットを追加」**
5. 右上の**「完了」**

ページが埋まっていて空き地が無いときは、アイコンを長押し →「ホーム画面を編集」でも
同じ編集の状態に入れる。

同じ「編集」の中の「カスタマイズ」は外観（ライト／ダーク／着色／クリア）を
変えるところで、3-4 のマトリクスで使う。

**1 ページにまとめて置く。** 見比べるため。

| 検索欄に入れる | 横にめくって出す名前 | サイズ |
|---|---|---|
| `CharaTime` | **スパイク A 静止** | 中のみ |
| 〃 | **スパイク B エントリ切替** | 中のみ |
| 〃 | **スパイク C 1 秒の点滅** | 中のみ |
| 〃 | **スパイク D 4fps** | 中のみ |
| 〃 | **スパイク E 切り分け**（3-6） | **大のみ** |
| 〃 | **スパイク F 1 本**〜**F 14 本**（3-7。1・2・4・6・8・14 の 6 枚） | 小のみ |
| 〃 | **スパイク F 組み方**（3-7） | 大のみ |
| 〃 | **スパイク G 透明**・**G 空**・**G ほぼ透明**（3-7） | 小のみ |
| `秒時計` | 秒時計 for Widget | 中 |

**検索はアプリの名前で引く。** ウィジェットの名前では引けない（`スパイク` と入れても
「検索結果なし」になる。2026-09-23、シミュレータで確認）。`CharaTime` で出てくる
1 件の中に、本番のウィジェット（CharaTime の小・中・大）と A〜G が並んでいる（18 枚。
3-2 で骨組みを本番のウィジェットに置き換えた）。

**本番の「CharaTime」は、スパイクの測定では置かない。** スパイクとは別のターゲットの別物で、
置くと電池の測定に本番のぶんが混ざる。

**秒時計を並べるのは切り分けのため**（3-1 の続き）。他社の実装がホーム画面で
秒を刻めているかどうかが、C が止まったときの読みを決める。
秒時計が動いて C が止まれば、原因は手法（マスク書体）の側にある。
両方止まれば、**ホーム画面では拡張の外から描き直されない**ということになる。

**Pixel Pals は無理に置かなくてよい。** 売りは Dynamic Island（面 3）で、
ホーム画面ウィジェットが秒単位で動く保証はない。面 1 の証拠にはならない。

#### 所見（2026-09-23、iPhone 17 Pro / iOS 26.1、ホーム画面）

**① 土台は生きている。秒カウンタが A〜D すべてで進んだ。**

これは「OS が描き直している」以上のことを言っている。**秒カウンタは
`entry.date` からの経過秒**なので、それが 0 より進んで見えること自体が、
**拡張が再実行されないまま画面だけ更新されている**という意味になる。
§2 の「2 つの読み」が答えを出した形で、3-1 のホーム画面の空欄もこれで埋まった。

**② 止まっているのはマスク書体のほう。**

| ウィジェット | ● の作り | 見えたもの |
|---|---|---|
| C | 1・2 番目はマスク付き、3・4 番目は素の消灯 ● | **薄い丸が 2 つだけ**。マスク付きの 2 つは一度も点かない |
| D | 4 つとも マスク付き | **丸が 1 つも出ない** |

どちらも**マスクが常に「隠す」側に倒れている**。秒の偶奇に関わらず、である。

**③ システムフォントへの落下ではない。**

§5 ② のとおり、`Font.custom` が黙ってシステムフォントに落ちた場合は
**マスクが数字の形になり、● の一部が見える**。何も見えないのだから、そうではない。
つまり「書体が無視された」のではなく、**切り出した窓に字形が入っていない**。

ウィジェットのタイマー文字は OS 側が組む。アプリ内とは確保幅や文字送りが違うため、
**右端 1em の窓が空白に当たっている**と考えるのがいちばん素直である
（下見画面では同じコード・同じ書体で点いた。差はレンダリング経路だけ）。

**④ これは `research/F` §2 の報告と整合する。**

「Xcode 26.1 以降の SDK でビルドすると止まる」という報告の、**止まっている中身が
分かった**。止まったのは**描き直し**ではなく、**タイマー文字への細工**のほうである。

**⑤ B は動いた。しかも公式の目安より細かい間隔で拾われている。**

● が 1 分ごとに 1 つ右へ進んだ。**最後の砦は生きている。**

見落とせないのは間隔である。スパイクの B は
`spacingSeconds = 60`・`entryCount = 60`、つまり**公式の目安（エントリは約 5 分以上）
より短い 1 分刻み**を、OS がどこまで拾うかを見るために置いたもの。それが拾われた。

**これはプラン §7.5 の土台を裏づける。** 本番の「5 分刻み × 4〜6 時間（48〜72 エントリ）」は、
OS が実際に拾う粒度より粗い側にある。しかも**更新予算に数えられるのはタイムラインを
作り直した回数**なので、1 本に何エントリ入れても費用は変わらない。
「10 分ごとに姿と位置が変わる」という面 1 の約束は、この線で払える。

ただし見たのは置いた直後の数分である。**時間が経っても拾われ続けるか**は別の話で、
そこは 3-4 の「1 時間放置」と Phase 3 の 3-7（1 週間の実機運用）で見る（R-2）。

**⑥ Reduce Motion の「リセット」は異常ではない。**

入／切のどちらに変えても A〜D の秒カウンタが振り出しに戻る。設定変更で
ウィジェットの再読込が走り、`entry.date` が現在に戻るためで、設計どおり。
秒時計が平気なのは、あちらが**絶対時刻**を出していて経過時間を出していないから。

ただし本番で経過時間を画面に出すなら、**ユーザーが設定を触るたびに見た目が飛ぶ**
ことは覚えておく（面 3 の「いっしょモード」の残り時間表示が該当する）。

### 3-5. 電池を見る（0-10）

**丸 1 日置いてから**、設定 → バッテリー → CharaTime の消費を見る。

- 24 時間での消費: ______ %
- 所見: __________________________________________

比較のため、スパイクのウィジェットを外した状態でも同じ日数を測れると理想だが、
1 日でだいたいの桁は分かる。

**追記（2026-09-23）: ここで測る意味は薄くなった。** この節は
「疑似アニメが電池をどれだけ食うか」を見るためのものだったが、**C・D が動いていない**
以上、食う当のものが動いていない。B だけなら通常のウィジェット更新と変わらない。

電池は Phase 3 の **3-7（1 週間の実機運用）**でまとめて見るほうが実になる。
本番のタイムライン（5 分刻み × 4〜6 時間）で、1 日 40〜70 回の予算に対して
実際どれだけ使うかを測れる（R-2）。

**追記（2026-09-23 夕）: E の α〜δ が実機で動けば、この節は生き返る。** 食う当のものが
動くことになるので、E を置いた状態で丸 1 日測り直す（3-6）。

### 3-6. スパイク E で切り分ける（2026-09-23 追加）

C・D は一度も点かなかったが、秒のカウンタは進んでいた（3-4 ①）。原因の候補は 3 つあり、
見た目では区別できなかった。

- (a) 拡張の中で書体が登録されていない
- (b) 書体は効いているが、切り出した窓が字から外れている
- (c) 毎秒更新されるタイマー文字を、マスクの材料にできない

**E の中身**（大 1 枚、8 行。コードは `Shared/SpikeProbe.swift`）

| 行 | 何を出すか | 何が分かるか |
|---|---|---|
| ① 止まった字 | 「05:24」をマスク書体で（動かない字） | 拡張で書体が効くか。(a) の確認 |
| ② 動く字 | C・D と同じ組み方（`.fixedSize()`）のタイマー文字を、切り出さずに | C・D の材料が描かれるか |
| ③ 動く字・枠あり | 枠を 8 字ぶんに決めて右寄せにしたタイマー文字 | 枠を決めれば描かれるか |
| ④ マスク 動｜止 | ③ の字（左）と ① の字（右）で、橙の帯にマスク | 動く字をマスクに使えるか。(c) の確認 |
| α 枠あり右寄せ | C と同じ ● の組を、③ の組み方で切り出す | **C の直した版** |
| β 左から5字目 | `.fixedSize()` のまま、左から数えて切り出す | 枠の幅に頼らない別案 |
| γ マスクなし | α の組み方で、字そのものを ■ にする | マスク抜きでも動くか |
| δ 4本ずらし | γ の作りで、0.25 秒ずつずらした 4 本 | **D の直した版**（4fps） |

α・γ・δ（と ③・④ の左）は**丸 1 日数え続ける**（時も出して最長 8 字）。1 時間で数え終わると
点滅も止まり、3-4 の「1 時間放置」を測れない。C・D・②・β は対照なので、元の 1 時間のまま。

#### シミュレータでの結果（2026-09-23、iOS 26.5・iPhone 17、ホーム画面に E と C を置いた）

**原因は (b) だった。`Text(timerInterval:)` に `.fixedSize()` を当てると、ウィジェットの中では
枠の幅が有限の値にならない。** 幅が無限の枠の「右端 1em」は画面のどこにも無いので、
C・D は何も映さなかった。アプリの中では枠が字にぴったりになるので、下見画面では点いていた。

分かった経緯: E の最初の版は ② の枠の幅を数字で出そうとして、その幅を整数にする所で
拡張ごと落ちた（`Double value cannot be converted to Int because it is either infinite or NaN`）。
幅を拾う `GeometryReader` を当てるだけでも、SwiftUI の中の検査で落ちた。
**測れないこと自体が答えだった。** いまの E は幅を測らない（落ちれば A〜D も巻き添えになる）。

| 行 | 見えたもの | 読み |
|---|---|---|
| ① | ■ ▯ ▯ ■ ■ | 書体は効いている。(a) ではない |
| ② | **何も出ない** | C・D の材料は、そもそも描かれていない |
| ③ | 字が枠の右端にそろい、毎秒変わる | 枠を決めれば描かれる |
| ④ | 左右とも ■ の形に色が抜ける | マスクは動く字でも効く。(c) ではない |
| α | **1 秒ごとに交互に点く** | **C の直した版は動く** |
| β | 点かない | `.fixedSize()` を使う限り駄目 |
| γ | 1 秒ごとに交互に点く | マスク抜きでも動く |

設計どおりの位相（0.25 秒刻み）に一致した。そのあいだ「絵を作ったのは」の時刻は変わらない。
**拡張が動いていないあいだに、画面だけが毎秒（δ は 1 秒に 4 回）描き直されている。**

1 枚だけ、秒の境目で α の 2 つが同時に点いていた。α の左右は別々のタイマーで、
OS はそれを 1 つずつ描き直すため、境目の一瞬だけ片方が先に進むことがある。失敗ではないが、
**複数のタイマーを組み合わせる絵には、ごく短いずれが出うる**（Phase 3 で絵を組むときの注意）。

## 5. 中身のしくみ

### マスクフォント

`tools/spike/make_mask_fonts.py` が fontTools で TTF を作る（3-7 で 3 本足して 5 本）。

- `CTSpikeMaskEven` — 偶数の数字（0,2,4,6,8）が 1em の塗りつぶし、奇数は空
- `CTSpikeMaskOdd` — その裏返し
- `CTSpikeMaskSet27`・`CTSpikeMaskSet012` — 数字の集まり {2, 7}・{0, 1, 2} だけが塗りつぶし（F）
- `CTSpikeGauge` — 数字 d を高さ (d+1)/10 em の棒で描く（F で桁の切り出しを目で確かめる）

作成日時を固定してあるので、作り直してもバイト列は変わらない。

すべてのグリフを 1em 幅にそろえ、**文字列の右端 1em だけを切り出す**。
右端は必ず秒の一の位で、その偶奇は秒の偶奇と同じ。

### 作りながら分かったこと（①② シミュレータ、③ 実機アプリ内、④ 実機ウィジェット、⑤⑥ シミュレータのウィジェット）

**① `Text(timerInterval:)` には合字（GSUB の `liga`）が適用されない。**

`research/E` §2.3 は「`:` + 2 桁を合字で 1 グリフにする」案を書いているが、
手元（Xcode 26.6 / iOS 26.5 シミュレータ）では効かなかった。

| 試したこと | 結果 |
|---|---|
| `Text("05:24")` にマスク書体 | 四角が出る。**合字は効く** |
| `Text("05:23")` にマスク書体 | 何も出ない。正しい |
| `Text(timerInterval:)` にマスク書体 | **何も出ない。合字が効いていない** |

タイマーの文字だけが別の経路で組まれているらしい。
そこで **合字をやめ、右端 1 文字を切り出す方式**に変えた。こちらなら合字が要らない。

**② フォントの PostScript 名（name ID 6）が無いと iOS は登録しない。**

`FontBuilder.setupNameTable` に `familyName` と `styleName` だけ渡すと
PostScript 名が入らず、`UIAppFonts` に書いても登録されない。
`Font.custom` は**黙ってシステムフォントに落ちる**ので、
マスクが数字の形になり、点滅しているように見えない。

**③ マスク書体は実機でも効いた（2026-09-22 確認）。**

`scripts/ios-device.sh --install --screen spike` で実機（iPhone 17 Pro / iOS 26.1）に
入れて下見画面を見たところ、**C の ● 2 つが交互に点いた**。
書体が `UIAppFonts` から登録され、右端 1 文字を切り出す方式が
シミュレータだけの現象ではないことが分かった。

**ただしこれで分かるのは「マスク書体が正しく効くか」だけ。**
アプリは自分で動いているので、`Text(timerInterval:)` が更新されるのは当たり前。
**スパイクの本題は「ウィジェット拡張が止まっていても OS が描き直すか」**で、
それはホーム画面にウィジェットを置いて実機で見るしかない。

**④ ところが、ウィジェットの中では同じ書体が効かなかった（2026-09-23）。**

アプリ内で点いた同じコード・同じ書体が、ホーム画面のウィジェットでは
**一度も点かなかった**（3-4 ②）。秒カウンタは進んでいるので、描き直しは起きている。

**③ と ④ の差はレンダリング経路だけ。** アプリ内は SwiftUI が自分で文字を組むが、
ウィジェットのタイマー文字は OS 側が組む。前者では効く細工が後者では効かない。
**この 1 行がスパイクの答えである。**

→ **⑤ で訂正。** 差を生んでいたのは経路そのものではなく、その経路での `.fixedSize()` の振る舞い。

**⑤ ウィジェットの中の `Text(timerInterval:)` に `.fixedSize()` を当てると、描かれない（2026-09-23）。**

アプリの中では、`.fixedSize()` を当てたタイマー文字の枠は字にぴったりの幅になる。
ウィジェットの中では**枠の幅が有限の値にならない**。その結果、

- 字は描かれない（E の ②）。右端を切り出しても何も無い（C・D）
- 幅を拾う `GeometryReader` を当てると、SwiftUI の中の検査で**拡張ごと落ちる**
- 幅を整数にしようとすると、Swift の実行時の検査で落ちる

**枠の幅を決めれば描かれる。** `.frame(width:)` で枠を決め、`.multilineTextAlignment(.trailing)` で
字を右端に寄せれば、最後の字の位置が決まり、右端 1em を切り出せる（`DigitCut.boundedTrailing`）。
字数は時間とともに増えるので、枠は最長の字数ぶん取る（1 日なら「24:00:00」の 8 字）。

同じ性質は、表題の横の秒のカウンタにも出ている。ウィジェットではカウンタが右端に行かず
表題のすぐ横に並ぶ。タイマー文字が行の残りの幅をすべて取り、字をその左から並べるため。
**Phase 3 で本番のウィジェットにタイマー文字を置くときは、必ず枠の幅を決める。**

**⑥ `configurationDisplayName` に文字列補間を直接書くと、拡張ごと落ちる（2026-09-23、F）。**

`.configurationDisplayName("スパイク F \(count) 本")` と書くと、書式付きの文字列（`LocalizedStringKey`）になり、
WidgetKit が実行時に止める（「Formatted text for `configurationDisplayName` is not supported」）。
拡張がウィジェットの一覧を返す前に落ちるので、足したウィジェットがギャラリーに出てこない（前の一覧のまま残る）。
**`String` に組み立ててから渡す**と通る。
`description` も同じ。

### 1 秒より細かくする方法（D）

起点を 0.25 秒ずつずらした 4 本を重ねる。`e` を起点からの経過秒とすると、
`j` 本目が点くのは `floor(e + j/4)` が偶数のとき。
点いている ● の数は `4 → 3 → 2 → 1 → 0 → 1 → …` と **0.25 秒ごとに変わる**。

1 秒に 4 回変われば 4fps。**● の数を数えるだけで速さが読める**ので、
写真に撮らなくても目で判断できる。
